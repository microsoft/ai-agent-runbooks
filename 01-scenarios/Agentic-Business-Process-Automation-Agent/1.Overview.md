# Agentic Business Process Automation Agent - Overview

## Scenario Overview

| Property | Value |
|---|---|
| **Scenario Type** | Cross-Domain Operations / Long-Running Document-Based Processes |
| **Agent Type** | Event-driven workflows with specialist agents, human review, and a conversational monitoring agent |
| **Harness** | GitHub Copilot harness in Microsoft Copilot Studio |
| **Primary Tools** | Microsoft Copilot Studio, Workflows, Dataverse, Power Apps code apps, Teams, Outlook |
| **Complexity** | Advanced |
| **Status** | Documentation and upstream accelerator available; tenant deployment and acceptance required |
| **Accelerator** | [microsoft/copilot-agentic-business-process](https://github.com/microsoft/copilot-agentic-business-process) |

This scenario uses **BusinessProcessCore** as a reusable runtime for document-heavy
business cases that span agents, workflows, and human decisions. **Order Processing**
is the available reference implementation: receive a purchase order, extract its
contents, review and correct the data, validate business rules, approve the evaluation,
and generate a downloadable SAP-shaped payload. It is not another accounts-payable
invoice scenario.

The additional value is the **case lifecycle around the reasoning**: persisted state
between short-lived stages, a customized human-in-the-loop (HITL) application, a shared
workflow/task queue and API for team- or role-based task allocation, safe claiming and
completion, and one process-agnostic monitoring agent. The same core can support other
domains without rebuilding those capabilities.

## Problem Statement

A claim, contract, loan, deal, tax case, or request for quotation (RFQ) rarely finishes
in one agent session. Documents arrive at different times, specialists correct data,
approvers change, and cases may remain open for more than 30 days. A document extractor
and an approval card alone do not provide a shared work queue, evidence-linked review,
durable case history, or a reliable answer to "where is this case and who holds it?"

Teams otherwise rebuild this plumbing for each business process and rely on individual
flow run histories to explain business decisions.

## Solution Summary

Install **BusinessProcessCore** once per environment. It supplies six Dataverse tracking
tables, a Business Process API, the Workflow Console Power Apps code app, and the
Business Process Monitoring Agent. Each business process adds its own stage workflows,
agents and skills, review-widget registrations, security roles, and configuration.

A stage records its result in Dataverse and ends. Creating a step row, or completing a
human-task step, triggers the next workflow. Human waiting time is stored state, not a
flow action held open. Teams notifications lead reviewers to the custom console; the
monitoring agent answers operational questions from the same recorded evidence.

**Duration boundary:** the architecture supports a business case outliving a single
flow run; it does not extend any platform run limit or promise unlimited retention.
Power Automate cloud flows have a documented
[30-day run duration limit, including pending approvals](https://learn.microsoft.com/en-us/power-automate/limits-and-config#duration-limits).
Check the limits applicable to the deployed Copilot Studio workflows separately.
A real greater-than-30-day resume test, connection continuity, retention, and recovery
validation remain release gates; they have not been executed for this runbook.

### Workflow and Task Coordination Across Teams

Complex cases can move between different functions and geographically distributed
teams rather than a single manager: for example, a regional intake team reviews the
documents, a specialist compliance team evaluates exceptions, and a central commercial
team gives final approval. Each stage can target its own team or capability role while
retaining one case identity, history, and evidence trail.

The shared **Workflow Console and Business Process API** turn these handoffs into
actionable work queues: eligible users see tasks they can claim, the first successful
claim establishes individual responsibility, and completion records the decision before
the next stage starts. Role membership can be held directly or inherited through a
Dataverse team, reducing reliance on hard-coded individuals or mailbox forwarding.

This is a reusable task-coordination foundation, not a prebuilt workforce scheduler.
The current API supports **self-claim**, not supervisor assignment to an arbitrary
person. Regional routing, shift coverage, reassignment, escalation, and workload
balancing need explicit process design or extensions. The reference assumes one
Dataverse business unit; distributed teams do not imply cross-tenant orchestration or
automatic regional data residency. See the [routing contract](2.Architecture.md#team--and-role-based-task-routing).

## How It Works

1. A business event creates a process instance, attachment, and initial step.
2. A step-triggered workflow invokes extraction and records structured output.
3. A reviewer claims the task in the Workflow Console, checks the source, and corrects
   the extracted data. Completion persists the decision and closes the human step.
4. The resulting event triggers policy validation using agent skills and knowledge.
5. A second human gate reviews the evaluation before final artifact generation.
6. Operations asks the monitoring agent about status, stale progress, assignments, and
   outputs across any authorized process using the core tracking contract.

## Reuse Beyond Order Processing

These are **customization candidates, not shipped implementations**.

| Candidate | Domain-specific customization | Human decision retained |
|---|---|---|
| Claims | Evidence intake, policy checks, damage/coverage assessment, settlement proposal | Authorized claims specialist approves the disposition and settlement |
| Contracts | Clause extraction, playbook checks, version comparison, negotiation package | Qualified counsel approves legal positions and any final agreement |
| Loans | Application/document completeness, financial evidence, underwriting policy checks | Authorized underwriter makes the lending decision under applicable controls |
| Deals | Due-diligence documents, commercial exceptions, pricing and approval package | Deal desk and authorized signatories approve commitments |
| Tax | Document reconciliation, jurisdiction-specific rules, exception review | Qualified tax reviewer approves advice, filings, and submissions |
| RFQ processing | Requirement extraction, supplier response comparison, quote assembly | Procurement/commercial owner approves selection and outward commitments |

**Forge-assisted agentic customization** is a delivery approach, not a bundled runtime
integration or a claim that Forge has already generated these solutions. Use the existing
accelerator codebase, identify reuse and gaps, and implement an approved domain backlog.
Keep domain rules out of the core; extend its console through review widgets when needed.
See the [customization path](3.Runbook.md#forge-assisted-agentic-customization).

## Target Users and Expected Outcomes

- **Reviewers and approvers:** a richer review experience than a basic approval card,
  with source evidence, corrections, ownership, and clear decisions; team- and role-based
  queues support handoffs across functions and locations.
- **Operations and process owners:** consistent case visibility across business domains,
  without opening individual maker flow histories.
- **Delivery teams:** reuse state, task lifecycle, and monitoring while adapting domain
  logic and UI through governed agentic development.
- **Audit and governance teams:** reconstruct inputs, outputs, stages, and human decisions
  from retained records. These records are not an immutable compliance archive by default.

Measure review effort, elapsed case time, stale-task age, exception rate, and trace
completeness during the pilot; no quantified improvement is asserted here.

## Scope and Boundaries

**Included:** core adoption, the Order Processing reference, custom HITL, process-agnostic
read-only monitoring, long-lived case design, and a Forge-assisted extension path.

**Not included:** ready-made implementations for every candidate domain; live SAP posting,
payment, loan approval, claim settlement, contract signature, or tax filing; automatic
retry/compensation or exactly-once execution across all stages; production SLA guarantees.
The order sample uses fictional catalog, inventory, and promotion data and generates an
SAP payload without posting it. Production connectors and domain controls require work.
