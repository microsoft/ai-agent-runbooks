# Agentic Business Process Automation Agent - Runbook

**Audience:** Power Platform delivery engineers, process owners, UI developers, and
operations owners. This runbook documents adoption and customization; no tenant
installation or acceptance execution is claimed.

## 1. Qualify and Pin the Accelerator

1. Use the [comparison](1.Overview.md#additional-value-compared-with-the-invoice-scenarios)
   to confirm that the requirement is a long-lived case with rich review, multi-team
   task coordination, or shared monitoring. For simple invoice intake and approval,
   prefer the existing invoice scenario instead of introducing this runtime.
2. Obtain the [upstream repository](https://github.com/microsoft/copilot-agentic-business-process)
   in an approved workspace and record the selected commit, core/process package versions,
   and applicable license. Follow its root and nested `AGENTS.md` guidance.
3. Read the core and Order Processing deployment guides linked in
   [source references](0.Resources/README.md). Those guides own the current commands,
   package names, connection references, and platform-specific repair steps.
4. Agree a stage map, intake sources, duration/retention expectations, reviewer roles,
   decision authority, data classification, and permitted external side effects.

**Exit:** the owner accepts the reference implementation's limits and the target
process's customization scope. Claims, contracts, loans, deals, tax, and RFQs are not
treated as prebuilt packages.

## 2. Confirm Readiness and Identities

| Requirement | Verify before installation |
|---|---|
| Environment | Approved Dataverse environment; code apps and the required Copilot Studio harness/workflow features available in the target region and tenant |
| Deployment access | Dataverse System Administrator or a validated deployment role; separate approved Entra app-registration rights; provisioning rights only if creating an environment |
| Runtime identity | Core service principal/application user with `Business-Process-User`, not System Administrator |
| Process connections | Dedicated automation user and approved Outlook, Teams, and agent-node connections; record connection owner and renewal responsibility |
| Licenses and capacity | Power Apps Premium for console users, appropriate Copilot Studio maker/automation entitlements, Teams, Exchange for order intake, and Copilot Credits |
| Administration | Exchange/User Administrator participation only when mailbox/user provisioning needs it; DLP and connector approval |
| Tooling | Power Platform CLI, Azure CLI, PowerShell 7, Python with uv; supported Node/npm or .NET SDK only when modifying the console or plug-in |
| Test users | Reviewer, approver, competing eligible reviewer, unauthorized caller, and operations user |

Use the upstream readiness report and current licensing guidance. Microsoft 365 Copilot
licensing does not by itself cover GitHub Copilot harness consumption. Keep credentials,
tenant identifiers, real documents, and deployment settings out of public source control.

## 3. Install and Verify BusinessProcessCore

1. In a sandbox, request the upstream `deploy-business-process-core` Copilot skill,
   or follow the manual [Core deployment guide](https://github.com/microsoft/copilot-agentic-business-process/blob/main/core/solution/DEPLOYMENT.md).
   Review its readiness report and explicitly approve the target and proposed writes.
2. Import core before any business-process solution. Reuse compatible identities and
   connections rather than creating replacements during redeployment.
3. Verify all six tracking tables, the task/process Custom APIs, effective runtime
   privileges, and the packaged Workflow Console.
4. Set `faf001_WorkflowConsoleBaseUrl` to the actual hosted console and test a task
   deep link. A published app alone is not proof of backend or user access.
5. Verify the monitoring agent's tool associations, then configure its publication,
   sharing, channel, authentication, and business-user access. An active imported
   agent alone does not establish that Teams users can use it.

**Exit:** authorized test callers can read permitted records, and an unauthorized
caller cannot. Record the deployed versions and verification evidence.

## 4. Deploy the Order Processing Reference

1. Use synthetic purchase orders and an isolated shared mailbox. Provision or reuse the
   approved automation account, licenses, mailbox permissions, and connections.
2. Request `deploy-order-processing`, or follow the
   [process deployment guide](https://github.com/microsoft/copilot-agentic-business-process/blob/main/business-processes/order-processing/solution/DEPLOYMENT.md).
   The skill can activate workflows: approve that operation only for the test environment.
3. Configure `faf001_OrderMailboxAddress` and verify all environment bindings.
4. Assign `Order Reviewer` and `Order Approver` roles, or the documented reviewer and
   approver teams, to test users. Verify both task eligibility and data permissions.
5. Check the four workflows, two published agents, and two console widget registrations.
6. Run receive -> extract -> correct -> validate -> approve -> finalize. Verify that the
   corrected data, not the original extraction, reaches validation and final output.
7. Download the SAP-shaped artifact and validate its schema. Do not report an SAP order
   as created: the reference does not post to SAP.

**Exit:** both human gates and the final artifact are traceable to one instance.
Replace fictional product, stock, and promotion data before business use.

## Configure Multi-Team Task Coordination

1. Agree a stage-to-function/location routing matrix, such as regional document review,
   specialist compliance review, and central approval. Record eligible Dataverse teams
   or exact capability roles, case/document permissions, and the accountable owner.
2. Select team-only or role-based routing for each unassigned task. Follow the
   [API eligibility contract](2.Architecture.md#team--and-role-based-task-routing):
   a required role takes precedence over assigned-team membership, so setting both
   fields does not restrict a broad role to one region.
3. Configure and test user-scoped queues, task deep links, and notifications separately.
   Team notification membership alone does not grant permission to claim or read a task.
4. Verify self-claim, start, completion, and downstream handoff across at least two
   functions or regional teams. Preserve a single case identity and the correct actor
   for each human decision.
5. Specify absence coverage, escalation, reassignment, and shift-handoff requirements.
   Treat any missing mechanism as a customization item; the existing claim API cannot
   assign to an arbitrary colleague. Validate organizational boundaries explicitly if
   the design goes beyond the reference's single-business-unit assumption.

## Forge-Assisted Agentic Customization

Use **Agent Forge's Agentic Customization path**, with separately installed and approved
Forge tooling: analysis -> solution design -> accelerator evaluation -> backlog ->
implementation. This is design-time assistance, distinct from the accelerator's
deployment skills and runtime agents. No Forge generation is executed by this runbook.

1. **Analyst:** capture the selected domain's documents, stages, rules, exception paths,
   consequential decisions, privacy boundaries, and measurable acceptance criteria.
2. **Architect:** design the process on BusinessProcessCore; specify intake events,
   unique step names, agent output schemas, data keys, widgets, reviewer roles,
   integrations, and the paths for reject, more information, failure, and replay.
3. **Implementation Recommender:** assess the accelerator against that design. Separate
   reusable core capabilities, customization of covered features, and uncovered gaps.
   Confirm the customization route before implementation.
4. **Product Owner:** create an approved backlog for domain skills/knowledge, workflow
   stages, data contracts, UI, security, integration, and operations work.
5. **Developer:** work in the existing accelerator codebase. Do not scaffold a replacement
   Azure project over it. Add a separate process solution; preserve the core tracking/API
   contracts and keep domain policy out of shared runtime logic.
6. Reuse generic review widgets where sufficient. Otherwise add a typed, domain-prefixed
   widget, register its ID, and agree input/output keys with downstream workflows.
   Console changes ship in the core app package; test existing process widgets too.
7. Follow the upstream solution-authoring approval and pack/import procedure. Repack
   changed solution exports; importing an old committed ZIP will not deploy local edits.
8. Run the existing validation harness for each changed surface. For console changes,
   use its documented `npm test`, `npm run lint`, and `npm run build`; validate workflow,
   plug-in, role, and package changes with the corresponding upstream guides and sandbox tests.

Keep irreversible actions separately authorized. Producing a settlement, contract,
credit recommendation, tax package, or quote must not silently authorize payment,
signature, lending, filing, or sending.

## Acceptance and Release Gates

**All cases below are required checks, not recorded passes.** Capture instance/task
IDs, actor, timestamps, versions, observed results, and supporting evidence.

| Case | Required result |
|---|---|
| Reference happy path | All four workflow stages, both reviews, corrected data, and final artifact belong to the same instance |
| UI review | Source and extracted values are usable together; corrections persist; failed submission preserves edits and shows an error |
| Competing reviewers | Two eligible users claim the same task; only one wins; a completion conflict does not duplicate outcomes or downstream effects |
| Multi-team handoff | Separate functional or regional teams receive their intended stage tasks; claiming establishes one assignee and completion advances the same case |
| Routing isolation | Test team-only routing, direct/inherited role eligibility, a user outside the intended region, and a notification-only recipient; enforce the approved scope without assuming role-plus-team intersection |
| Decision branches | Rejection prevents finalization; `needs_info` follows an explicitly designed path, never implicit approval |
| Authorization | Unauthorized users cannot read evidence, claim, or complete tasks; monitor results respect the intended caller's access |
| Monitoring reuse | Query two different process names using the same agent; no order-specific schema/prompt changes; mutations are refused |
| Long wait | Retain a genuinely waiting task for more than 30 elapsed days, then complete it and verify a new stage run resumes the same instance with its evidence intact |
| Recovery and replay | Inject a failed stage, duplicate intake, and duplicate event; detect failure, recover under the approved procedure, and prevent duplicate business side effects |
| Data and model safety | Missing/malformed documents or outputs stop explicitly; embedded instructions cannot bypass a human gate or trigger unauthorized tools |
| Version and retention | An older open case remains reviewable after an approved upgrade; evidence survives the configured retention period and disposal is controlled |

Backdating timestamps or a compressed wait can test logic, but **does not certify
greater-than-30-day operation**. Keep that capability unverified until the elapsed-time
test passes. Do not infer stage idempotency from the task API's concurrency protection.
If a reference branch lacks the target recovery or more-information behavior, implement
and test it before declaring that requirement supported.

## Operations and Rollback

Assign owners for stale-case thresholds, connection/credential renewal, failed triggers,
Copilot Credit consumption, storage, access reviews, and evidence retention. The
monitoring agent provides conversational visibility, not proactive SLA alerting or
automatic remediation.

Promote only approved packages after acceptance. Retain the previous core/process/app
versions and test rollback compatibility with open cases. On an incident, pause affected
intake or stage triggers under the operations procedure, preserve tracking records and
evidence, and inspect partial side effects before replay. Do not delete the environment
or uninstall the core as a production rollback; tracked records can cascade-delete.
