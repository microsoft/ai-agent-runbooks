# Autonomous Invoice Orchestration Agent — Architecture

## 1. Logical Architecture

The three layers are the submitters, mailbox and approver at the edge, the Copilot Studio GitHub Copilot agent, and the workflow, document library and Dataverse table that the agent and the workflow use. The agent is not a chat agent. It has no end-user channel and is called only by one workflow.

One configuration includes the workflow **Invoice Intake and Approval** and the two skills. Operators build the Dataverse table, the SharePoint folders, the agent and the workflow in the tenant. The workflow owns the trigger, the saved original, the completeness check, the approval and the reply to the sender. The agent owns reading the PDF and writing the Dataverse row and the review JSON file. No custom backend is required or supplied.

## 2. Key Components

| Component | Technology | Role |
|---|---|---|
| Event entry | Office 365 Outlook **When a new email arrives (V3)** in Copilot Studio Workflows | Starts the workflow for each email with attachments in the invoice mailbox. The mailbox and the identity are configured during setup |
| Workflow | Copilot Studio Workflows, **Invoice Intake and Approval** | Saves each PDF, calls the agent, checks the returned JSON, starts the approval or replies to the sender. It is the only workflow |
| Agent call | Workflows Agent node, **An existing agent** | Calls the published Autonomous Invoice Orchestration Agent with the PDF path, the PDF link, the email subject and the sender, and waits for its JSON response |
| Agent runtime | Copilot Studio GitHub Copilot harness | Reads and reasons over the invoice and follows the skill procedures. It is not Copilot CLI or a Copilot SDK host |
| Skills | Two standalone definitions | `invoice-extraction-review` (extraction, checks and the Dataverse row) and `save-invoice-json-to-sharepoint` (review JSON and Review Link). Each skill is one capability |
| Agent tools | SharePoint MCP, Dataverse MCP and the `CreateSharingLink` tool in the agent | Read a file from its link, create a view-only sharing link, create and update rows on one table, read the environment variables and create a file in `/Invoices/Reviews` |
| Document library | SharePoint document library | Holds the original PDFs in `/Invoices/Sources` and the review JSON files in `/Invoices/Reviews` |
| Data store | Dataverse table **Auto Invoice Review** | One row per run with the 18 columns and the native row ID defined in the [data model](0.Resources/Capability-matrix.md#dataverse-data-model) |
| Approval | Approvals connector **Start and wait for an approval** in Workflows | Sends the fields, issues and links to the approver and records the outcome |
| Sender reply | Office 365 Outlook **Reply to email (V3)** in Workflows | Tells the sender which fields are missing, once per PDF |
| Monitoring | Workflow run history, agent run history, approval records and the mailbox | Operators inspect failures and uncertain outcomes. No custom queue or status API exists |

### Capability Design

| Capability | Component | Behavior and controls |
|---|---|---|
| Invoice capture | Workflow trigger and SharePoint **Create file** | Keeps PDF attachments only, saves each under a stable name in `/Invoices/Sources`, and passes the full path, the link, the email subject and the sender to the agent. A message without a PDF ends the run without a reply |
| Invoice extraction and record | `invoice-extraction-review` | Reads the invoice from a chat attachment or a SharePoint link, creates a sharing link for the Source Link, extracts 11 fields and leaves a missing field empty. Derives Issues Found, a Summary and a Decision (`READY_FOR_APPROVAL` only when all 11 are found) and creates one row in the Auto Invoice Review table |
| Review JSON file | `save-invoice-json-to-sharepoint` | Runs only when the prompt carries the email subject, sender, PDF path and PDF link. Reads the site and folder from environment variables, writes an 18-key JSON file to the Reviews folder and stores its sharing link in the row's Review Link |
| Completeness check | Workflow condition | Applies the [completeness rule](0.Resources/Capability-matrix.md#completeness-rule) to the returned JSON. The Decision must be `READY_FOR_APPROVAL`, Issues must be empty and the other keys must have values. `null`, absent and blank are missing, `0` is a value. The workflow, not the agent, decides who is notified |
| Approval | Workflow Approvals action | Starts only for a complete invoice. The approver sees the invoice key, vendor, amount, due date and summary, with links to the source PDF and the review file |
| Missing-information reply | Workflow Outlook reply action | Replies to the sender with the missing field names and the stored PDF name, and asks for a corrected invoice |
| Failure follow-up | Workflow owner | A response that is not the expected JSON, or a complete invoice without a source or review link, ends the run as failed. The owner inspects run history and handles the invoice manually |

The design uses one agent and one workflow. No connected agent, ERP feed, payment system or general mailbox search is needed.

### Capabilities and Workflow Configuration

The [matrix](0.Resources/Capability-matrix.md) records the agent's tools, the eight workflow steps, the JSON response contract, the completeness rule and the data model. The agent's tools are configured in **Build > Tools**. Outlook, SharePoint save and Approvals operations belong to the workflow, not to the agent.

The [Workflows Agent-node guidance](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/agent-node-workflow) documents selecting an existing published agent and using its response in the workflow. Before the workflow is turned on, operators verify the selected agent and version, the output form (custom structured output or Parse JSON), the effective identity of the agent's tool connections, and that the harness reads the PDF content returned by the SharePoint tool. [Resources](0.Resources/README.md#release-gates) lists these checks as release gates.

## 3. Data Flow

### Scenario A — Complete Invoice and Approval

```mermaid
sequenceDiagram
    participant Mail as Outlook Invoice Mailbox
    participant Flow as Copilot Studio Workflows
    participant Agent as Autonomous Invoice Orchestration Agent
    participant Store as SharePoint and Dataverse
    actor Approver as Approver
    Mail->>Flow: New email with a PDF attachment triggers workflow
    Flow->>Store: Saves the PDF to /Invoices/Sources
    Flow->>Agent: Passes the PDF path, link, subject and sender
    Agent->>Store: Reads the PDF, saves the row and the review JSON
    Agent-->>Flow: Returns JSON with every field
    Flow->>Flow: Checks that Decision is READY_FOR_APPROVAL and no value is missing
    Flow->>Approver: Starts approval with fields, summary and links
    Approver-->>Flow: Approves or rejects
```

This is the routine path. The workflow starts the approval only when the agent set Decision to `READY_FOR_APPROVAL`, Issues is empty and every key has a value. The approval outcome stays in the approval record and the run history. The workflow does not pay the invoice and does not send an outcome email.

### Scenario B — Missing Information and Reply to the Sender

```mermaid
sequenceDiagram
    actor Sender as Invoice Submitter
    participant Mail as Outlook Invoice Mailbox
    participant Flow as Copilot Studio Workflows
    participant Agent as Autonomous Invoice Orchestration Agent
    participant Store as SharePoint and Dataverse
    Sender->>Mail: Emails an invoice without a purchase order number
    Mail->>Flow: New email triggers workflow
    Flow->>Store: Saves the PDF to /Invoices/Sources
    Flow->>Agent: Passes the PDF path, link, subject and sender
    Agent->>Store: Saves a NEEDS_REVIEW row and the review JSON
    Agent-->>Flow: Returns JSON with Decision NEEDS_REVIEW and the issue
    Flow->>Mail: Replies to the sender listing the missing fields
    Mail-->>Sender: Receives the missing-information email
```

This diagram shows the missing-information path. No approval starts. The row stays in Dataverse with Decision `NEEDS_REVIEW`, and a corrected invoice from the sender is processed as a new email. Nothing looks for the earlier row, so the corrected invoice creates another row and another review file.

Other outcomes are summarized here. A response that is not the expected JSON, or a complete invoice without a `sourceLink` or `reviewLink`, ends the run as failed and leaves the saved PDF and any rows or files already written. An email with no PDF attachment ends the run without a reply. See the [outcome handling](0.Resources/Capability-matrix.md#outcome-handling), the [limitations](0.Resources/Capability-matrix.md#limitations-and-operational-ownership) and the [Runbook](3.Runbook.md).

## 4. Security & Governance Considerations

| Area | Consideration |
|---|---|
| Identity | The agent's SharePoint and Dataverse connections use a dedicated service account, not a maker's personal account and not the email sender. Whether workflow-invoked runs use that connection is a release gate. The workflow's Outlook, SharePoint and Approvals connections are owned and reviewed separately |
| Access control | Table scope and connection permissions limit what the agent can write. The agent's account has read rights on the Invoices library, contribute rights on `/Invoices/Reviews` only and create, read and write rights on one table. These limits do not rely on instructions alone, because the skills do not check paths |
| Untrusted input | Email text and PDF content are data. The agent receives only the PDF path and link that the workflow built, plus the email subject and sender as data. It never receives the email body. Text in a PDF that tries to give instructions is ignored and recorded as an issue |
| Authorization and writes | The agent has no email, approval or second-workflow tool. The workflow decides the approval and the reply from the returned JSON. A person approves each invoice that is complete, and no payment is made |
| Reliability | The saved file name is stable if the trigger fires twice. There is no duplicate detection, so a repeated invoice or a trigger that fires twice for one email can create a second row and a second review file. A partial failure ends the run as failed and leaves what was already written |
| Data handling | Invoices hold vendor, amount and tax business data. Limit access to the mailbox, the library, the table and the run histories, and set retention for originals, reviews and rows. Keep memory and unrelated personal-context retrieval off |
| Deployment | Use a dedicated mailbox and an optional sender allowlist. Verify the tenant, model, credits and Approvals availability, then pilot with synthetic invoices before real ones |
| Disablement | Turn off the workflow first. Then remove the agent's tool exposure or unpublish the agent. Removing a skill does not revoke tool permissions. Keep written files and rows |

### Identity, Permissions and Data Handling

**Mailbox identity:** the Outlook trigger and the reply use the connection of the account that owns the invoice mailbox. Verify the monitored folder and the sending rights. Receiving mail does not automatically grant the right to reply, and a shared mailbox needs its own address in the reply action.

**Agent identity:** the SharePoint and Dataverse tools run under the connection configured for the agent. Grant that account only the rights listed above. A write by the agent is therefore limited by the account, not by a prompt.

**Workflow identity:** the workflow saves the original PDF and starts the approval under its own connections. The approval title and details use values extracted from an untrusted PDF, so the approver assignment is fixed in the workflow and never taken from the PDF, and the approver compares the values with the source PDF.

**Sender identity:** a sender's display name can be forged, and the reply goes to the sender of the received message. The approver gets the link to the source PDF. A sender allowlist and the mailbox's own anti-spoofing controls are the first line of defense.

### Reliability and Deployment Boundaries

| Concern | Current limitation / operator action |
|---|---|
| Duplicate triggers | The stable file name avoids a second original, but nothing prevents a second row. Inspect the run history if an email shows two runs and delete the extra row |
| Loops and bounces | The workflow ignores mail from the mailbox itself and replies only when a PDF was processed. Review auto-responders, which can reply to the reply |
| Rate limits and concurrency | The attachment loop runs one file at a time. Inspect connector throttling and retries. No custom rate limiter or queue exists |
| Unreadable invoices | The agent saves a `NEEDS_REVIEW` row with issues, and the workflow replies to the sender. A response that is not valid JSON ends the run as failed. Missing values are never filled in |
| Wrong values that are present | The completeness check finds only missing values. The approver compares the extracted fields with the PDF |
| Approval outcome | The result is in the approval record and the run history. It is not written back to Dataverse |
| Maintenance / rollback | Disable the workflow, inspect runs in flight, then remove tool exposure or unpublish the agent |
| Cost and capacity | Workflow runs, agent runs and the approval wait use Copilot Credits and platform limits. Verify environment, model and credits |

The runbook leaves the workflow off until the agent, the non-sending checks and the pilot approval are ready. This documentation claims neither tenant execution nor production readiness.
