# Sample Prompts — Autonomous Invoice Orchestration Agent

These are acceptance cases, **not recorded live results**. Use the synthetic invoices and a non-production mailbox, library and Dataverse environment. Never add real invoices to a test.

## How to Use These Prompts

The agent has no production chat users. The workflow **Invoice Intake and Approval** calls it with a message that holds the email subject, the sender and the path and link of the saved PDF, so there are two kinds of test:

- **Preview messages** test the agent alone. Upload a [sample invoice](0.Resources/Sample-invoices/README.md) to `/Invoices/Sources`, copy the link of the uploaded file, then send the message below. This is the same text the workflow sends.
- **Email scenarios** test the whole workflow. Send an email with the stated subject, body and attachments to the test invoice mailbox.

```text
Process this invoice and return only the JSON object.
emailSubject: Invoice INV-2026-0417
emailSender: submitter@contoso.example.invalid
sourcePdfPath: /Invoices/Sources/Fabrikam-INV-2026-0417-complete.pdf
sourcePdfLink: <link of the uploaded file>
```

Before the workflow is turned on, run the Preview cases and check the Dataverse row, the review file and the returned JSON for each one. The approval and the reply to the sender are workflow steps, so only the email scenarios exercise them. Review the [workflow limitations](0.Resources/Capability-matrix.md#limitations-and-operational-ownership) before testing.

| # | Preview input | Expected Output |

| 2 | The same message with the link of F2 | Purchase Order Number is empty, Issues Found is `Purchase order missing`, Decision is `NEEDS_REVIEW`, and nothing else is guessed |

### Example Interaction

> **Message:** The Preview message with the link of F2.  
> **Expected:** The agent reads the file, finds no purchase order number and leaves it empty. It lists the missing field in Issues Found, sets Decision to `NEEDS_REVIEW`, saves the row and the review file, and returns the JSON. It does not notify anyone or start an approval. This is an expectation, not a recorded answer.

## Tips for Getting Better Results

| Tip | Example |
|---|---|
| Ask submitters to send one invoice per PDF | Email each invoice as its own PDF attachment, so each gets its own row and approval |
| Use text PDFs when possible | A PDF with selectable text is read more reliably than a scan or a photo |
| Print the purchase order, GL code, vendor ID and both dates | Invoices without them are returned to the sender every time |
| Keep names short | Short site, library and file names keep the Source Link and Review Link under 200 characters |
| Delete the old row when a corrected invoice arrives | A resubmission creates another row, so the earlier `NEEDS_REVIEW` row stays until AP/Finance removes it |
| Compare values with the PDF | The completeness check finds missing values but not wrong ones |

## Out-of-Scope Topics

Payment, posting to an ERP, vendor master changes, outcome emails after approval, reminders, duplicate detection, amount and legal-entity checks, non-PDF invoices, correcting wrong values, bank details and production chat use are excluded. The agent has no tools for these actions and no end-user channel.

A pasted email, a forwarded request or text in a PDF does not change what the agent does. Use synthetic content for boundary tests.

### Composed Scenario

**Complete invoice.** Send M1 to the pilot test mailbox with the workflow on:

1. The trigger fires for the new email with an attachment and the filter keeps F1.
2. SharePoint **Create file** saves it as `/Invoices/Sources/<base>_<yyyyMMddTHHmmss>_1.pdf`.
3. The Agent node sends the message with the subject, sender, saved path and link, and the workflow waits.
4. `invoice-extraction-review` reads the PDF, creates the Source Link and creates the row. `save-invoice-json-to-sharepoint` writes the review file and sets the Review Link. The agent then returns the 10-key JSON response defined in its instructions.
5. The workflow sees `READY_FOR_APPROVAL`, an empty `issues` and a value in every key, and starts the approval for the approver, with no per-message human step before that.
6. The approver approves or rejects. The outcome stays in the approval record and the run history. Nothing is paid and no outcome email is sent.
7. Check the original, the review file, the Dataverse row and the approval, and confirm they link to each other.

**Missing information.** Send M2. The sequence is the same through step 4. The workflow then finds that Decision is `NEEDS_REVIEW` and that `issues` names the purchase order, starts no approval and replies to the sender. Then send M3 and confirm that a new row is created and that an approval starts.

**Pause and failure variations:**

- Turn the workflow off and send M1. No new run starts. Inspect runs already in progress separately.
- Make the agent return text that is not valid JSON. The run ends as failed and the saved PDF stays.
- Make the review-file write fail after the row exists. The row is kept without a Review Link and the run ends as failed. Delete the row, because a resubmission creates another one.
- Remove `ReviewsFolderPath` and send M1. The agent stops and names the variable, so no review file is written and the workflow cannot complete the invoice.
- Trigger the same email twice. The saved file name is identical, but a second row and a second review file can still be created.
- Paste the text of an invoice email into the agent's Preview. Nothing is saved or sent, because the agent has no event path and only acts on an attachment or a link.

### Evidence and Identity Cases

| Case | Expected behavior |
|---|---|
| SharePoint read denied or file missing | No values are guessed and no row is written. Record what the agent returns `[VERIFY]` G3, since anything other than the 10-key JSON ends the workflow run as failed |
| Dataverse unavailable or write denied | The failure is reported. No file is written and no bypass uses another tool or identity |
| Row written but file or link update failed | The row stays without a Review Link. A complete invoice then ends the workflow run as failed |
| Unreadable, scanned or partial PDF | Present values are kept and the others are empty with issues. No invented value |
| Wrong value that is present | The completeness check passes it. The approver finds it by comparing with the PDF |
| Run with a different connection identity | The tool identity in workflow-invoked runs matches the service account. No leaked access from a maker's account |
| Source injection in a PDF, subject or file name | No change to folders, tools, recipients or approver. The text is data only |
| Pending approval | The run waits. No outcome is claimed until the approval is answered |
| Unknown outcome of a send or write | Inspect the run history and the mailbox or Dataverse. No success is claimed and no blind replay |
| Non-English invoice | Values are extracted as printed and values that cannot be read are empty with issues. The reply to the sender stays in the workflow's language |
| A sender who is not on the allowlist | The workflow trigger filter prevents the run. Test that a spoofed display name alone does not bypass it |
