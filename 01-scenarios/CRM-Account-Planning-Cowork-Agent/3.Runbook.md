# Step-by-Step Guide — CRM Account Planning Cowork Agent

> **Scenario**: Copilot Cowork + MCP server over the CRM, producing branded Office artifacts
> **Platform**: Microsoft 365 Copilot Cowork · MCP · Organization Asset Library
> **Target Readers**: Delivery engineer, solution architect
> **Estimated effort**: 4–6 weeks, of which the MCP server is the largest single item

---

## Prerequisites

| Requirement | Owner |
|---|---|
| Cowork available and enabled for the pilot group | M365 admin |

## Phase 0 — Discovery and Scoping (Week 1)

### Step 0-1. Prove the connector is insufficient

Do this before proposing an MCP server. It is a short exercise that saves a long argument.

1. Configure the standard CRM connector or first-party sales agent in a sandbox.
2. Attempt five real account-planning questions.
3. Record, for each: what data was reachable, what was not, and specifically whether custom
   objects and custom fields were accessible.

| # | Question | Data reachable | Blocked by |
|---|---|---|---|

You are looking to demonstrate one or more of: standard-fields-only exposure, no custom object
access, no aggregation, no write. Once shown, the MCP decision is a conclusion rather than a
preference — and it survives review.

### Step 0-2. Define the artifacts

Get the actual documents. Not descriptions of them — the files.

| Artifact | Current effort | Sections | Data required | Template exists? |
|---|---|---|---|---|
| Account plan | | | | |
| QBR deck | | | | |
| Pipeline review | | | | |

For each section of each artifact, name the CRM objects and fields it needs. This table becomes
your tool design in Phase 2 and your evaluation set in Phase 4.

### Step 0-3. Decide read-only vs read-write

Write access roughly doubles the security review, the approval design, and the test burden.
A defensible sequencing is: **read-only for the pilot, write-back as phase two**, once the
retrieval quality is proven and the identity model is validated.

Record the decision and the reasoning.

> ✅ **Exit criteria:** connector gap evidenced, artifacts and their data requirements mapped,
> read/write scope decided, spend position agreed.

## Phase 1 — Identity and Authentication Spike (Week 1–2)

Do this **before** building tools. It is the item most likely to force a redesign.

### Step 1-1. Establish what identity the server actually receives

1. Stand up a trivial MCP server with a single tool: `whoami`, returning the caller identity it
   observes.
2. Register it as a plugin.
3. Invoke it from Cowork, as a normal user who is not the developer.
4. Record exactly what arrived: a user token, a managed identity, or nothing useful.

This five-line tool answers the question that architecture diagrams cannot.

### Step 1-2. Design the token flow

Based on what you observed:

| Observation | Design |
|---|---|
| Per-user token available | OAuth on the MCP server, exchange for a user-scoped CRM token, cache with refresh |
| Only a service identity available | Either accept a scoped service identity with a restricted audience, or place the user consent at the MCP server itself and maintain a user-to-CRM-token mapping |
| Inconsistent between surfaces | Pin the scenario to the surface that works; document the constraint |

### Step 1-3. Confirm protocol version compatibility

Record the MCP protocol version supported by the host, by your server framework, and by any
gateway in the path. A mismatch surfaces as an authentication failure with no version
diagnostic, so establishing this now is worth an hour.

| Component | Protocol version |
|---|---|
| Host (Cowork / Copilot) | |
| Your MCP server | |
| Gateway (if any) | |

> ✅ **Exit criteria:** `whoami` evidence captured, token flow designed, protocol versions
> reconciled, security stakeholder briefed on the identity model.

## Phase 2 — Build the MCP Server (Week 2–3)

### Step 2-1. Design the tools

Start from the artifact table in Step 0-2 and work backwards. Target **5–8 tools**.

For each tool, write this down before writing code:

| Field | Content |
|---|---|
| Name | Verb-noun, unambiguous |
| Description | One or two sentences, written for a model choosing between tools. Say what it returns and when to use it |
| Inputs | Minimal, strongly typed |
| Output shape | Explicit field list. Never "the record" |
| Approximate payload size | Keep it bounded — the token window truncates |
| Read or write | Writes need confirmation semantics |

Two rules that pay for themselves:

- **Compose server-side.** If an account plan needs data from six objects, that is one
  `get_account_360` call, not six tool calls the model has to sequence.
- **Bound every payload.** Return the top N with a total count, never the full list. Truncation
  in the token window is silent and produces confidently incomplete artifacts.

### Step 2-2. Write the plugin description

If the tenant has more than five plugins, plugin selection is driven by the **plugin
description**, not by the tool names. Write it as the answer to "when should Copilot use this?"

Weak: *"Salesforce integration."*
Better: *"Retrieves account, opportunity, and pipeline data from Salesforce, including custom
objects, for account planning, QBR preparation, and pipeline review. Use for any question about
customers, deals, renewals, or territory performance."*

### Step 2-3. Implement, with observability from day one

Tool-call failures in agent contexts are notoriously opaque — partial completion with a generic
error is a widely reported experience. Instrument accordingly:

- Log every tool call: caller, tool, inputs (redacted), duration, outcome.
- Return **structured, actionable errors**. "Opportunity 006xx not found or not visible to this
  user" beats "request failed".
- Make writes **idempotent**, keyed on a client-supplied identifier. Retries after a partial
  failure will happen, and duplicate records are the result if you skip this.
- Emit traces to Application Insights or equivalent.

### Step 2-4. Test the server standalone

Before it goes anywhere near Cowork:

| Test | Pass criteria |
|---|---|
| Each tool returns correct data for a known account | Verified against the CRM UI |
| Per-user scoping | User A cannot retrieve User B's restricted records |
| Payload size | Every response within your bound |
| Error handling | Every failure mode returns a structured, readable error |
| Write idempotency | Same request twice produces one change |
| Latency | Each tool responds within a few seconds |

> ✅ **Exit criteria:** 5–8 tools, standalone tests passing, observability live.

## Phase 3 — Connect to Cowork (Week 3–4)

### Step 3-1. Register and deploy the plugin

1. Package the plugin manifest pointing at your MCP server.
2. Deploy it through the admin path so it is governed and inventoried, rather than
   user-installed.
3. Scope availability to the pilot group.
4. Verify it appears for a pilot user who is not you. Plugin and agent discoverability has been
   inconsistent in practice — check, do not assume.

### Step 3-2. Decide dynamic vs pinned tools

| Choose | When |
|---|---|
| Dynamic discovery (default) | You are iterating and want server changes live immediately |
| Pinned tool set | You need a change-control boundary between server deployments and agent behaviour |

If you keep dynamic discovery, add a rule to your release process: **every MCP server deployment
triggers a re-run of the evaluation set.** A server change is an agent change.

### Step 3-3. Build the custom skills

This is where the organization's opinion about an account plan is encoded. Create one custom
skill per artifact. Starting point for the account plan skill:

```text
ACCOUNT PLAN STRUCTURE

When asked to build an account plan, produce a Word document with exactly these
sections, in this order:

1. Executive summary — 5 bullets maximum, no CRM jargon
2. Account overview — industry, size, relationship history, current products
3. Current state — open opportunities with stage, value, close date, owner
4. Renewal position — dates, risk, and the reason for the risk assessment
5. Relationship map — key contacts, roles, last interaction date
6. Recent engagement — meetings and correspondence from the last 90 days
7. Risks and blockers — each with a named owner
8. Next best actions — maximum 5, each with an owner and a date

RULES
- Use the corporate Word template from the organization asset library.
- Every factual claim must be traceable to CRM data or a Microsoft 365 source.
  If the data is missing, write "Not recorded in CRM" — never estimate.
- Do not invent contact names, deal values, or dates.
- Do not include competitive intelligence unless it exists in a source you retrieved.
- Keep the whole document under four pages.
```

The "Not recorded in CRM" rule matters more than it looks. Without it, gaps in CRM hygiene get
filled with plausible fiction, and a seller takes it into a customer meeting.

### Step 3-4. First end-to-end run

Pick one well-maintained account and one poorly maintained account. Run both. The second one
tells you far more.

## Phase 4 — Evaluate (Week 4–5)

### Step 4-1. Build the evaluation set

At least 20 accounts, deliberately spanning:

- 5 well-maintained accounts
- 5 with sparse or stale CRM data
- 3 with heavy custom-object usage
- 3 with complex hierarchies (parent/child, partner-sourced)
- 2 the seller knows intimately, so they can catch subtle errors
- 2 with restricted records the requesting user must not see

| # | Account | Type | Artifact | Accuracy | Completeness | Brand compliant | Consistent ×3 |
|---|---|---|---|---|---|---|---|

### Step 4-2. Score on four axes

| Axis | Question | Failure means |
|---|---|---|
| **Accuracy** | Is every stated fact correct? | Any fabricated number or name is a hard fail |
| **Completeness** | Was material data missed? | Usually a tool-design or truncation problem |
| **Brand compliance** | Correct template, fonts, logos? | Go to the branded artifact pattern |
| **Consistency** | Same request, three runs, comparable output? | Non-determinism to diagnose before rollout |

### Step 4-3. Have sellers review, not engineers

An engineer checks that the deck was produced. A seller notices that the renewal date is wrong,
that a key contact left six months ago, and that slide four would embarrass them in front of a
customer. Route every pilot artifact through someone who would actually present it.

### Step 4-4. Permission verification

Run the evaluation as a user with restricted CRM access. They must not receive data outside
their CRM permissions. Record the evidence; security review will ask.

## Phase 5 — Compliance and Go-Live (Week 5–6)

### Step 5-1. Compliance position

Work through this with the compliance stakeholder **before** broad enablement:

| Question | Position |
|---|---|
| What is logged when the agent creates a document or updates a record? | |
| Are generated artifacts subject to retention and hold? | |
| Do the output formats in use support sensitivity labelling? | |
| Can the full chain of an autonomous task be reconstructed? | |
| Who is accountable for the content of a generated artifact? | |

Where a gap exists, constrain the scenario rather than assume it away — for example, restrict
output to formats that are covered by labelling, or require the artifact to be saved to a
governed location.

### Step 5-2. Approval design

Confirm before go-live:

- Every write to the CRM requires explicit confirmation.
- No artifact is sent externally without human review.
- A single request cannot modify more than a small, capped number of records.
- Users know how to interrupt and cancel a running session.

### Step 5-3. Set expectations at launch

Publish a short note covering:

| Topic | What to say |
|---|---|
| What it does | The three artifacts, named |
| How long it takes | Minutes, not seconds. Not a chat turn |
| What it will not do | Forecast numbers, certified reporting, external send without review |
| What to do when it is wrong | The feedback route, and that "Not recorded in CRM" means fix the CRM |
| Reliability | Be honest if the platform is in an early-access programme. Trust survives a known limitation; it does not survive a surprise |

### Step 5-4. Operate

| Cadence | Activity | Owner |
|---|---|---|
| Weekly (first month) | Review generated artifacts for accuracy drift | Delivery engineer |
| Weekly | MCP server error rate and latency | Platform team |
| On every MCP deployment | Re-run the evaluation set | Delivery engineer |
| Monthly | Cowork consumption against budget | M365 admin |
| Monthly | Time-saved measure against the Phase 0 baseline | Sales ops |
| Quarterly | Template and custom-skill review | Brand + revenue ops |
