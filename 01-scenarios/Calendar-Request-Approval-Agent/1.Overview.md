# Calendar Request Approval Agent - Overview

## Scenario Overview

| Attribute | Value |
|---|---|
| Scenario Type | Employee productivity / governed calendar requests |
| Agent Type | Conversational intake with deterministic workflow orchestration |
| Primary Tools | Copilot Studio, Power Automate, SharePoint Online, Office 365 Outlook |
| Complexity | Intermediate; identity and recovery controls require tenant-specific configuration |
| Status | Available |
| Last Updated | September 25, 2026 |

The underlying solution is complete and working. This folder documents a reusable
implementation path; configure and validate it for each target tenant.

Collect a calendar request in natural language, confirm its details, apply an
approval policy, and publish the result to the appropriate SharePoint calendar
and an explicitly authorized Outlook calendar.

The agent handles conversation, not authorization. Power Automate applies the
request-type and approval rules. SharePoint records the request and its outcome.

## Problem Statement

Calendar requests arrive through chat, email, and informal conversations.
Approvers lose context, employees cannot distinguish submission from approval,
and shared calendars become inconsistent with the original request.

This scenario provides a single intake contract and a traceable handoff from
request to decision to publication.

## Solution Summary

| Stage | Responsibility |
|---|---|
| Intake | Collect request type, subject, start/end, and optional notes; resolve ambiguity |
| Confirmation | Show absolute dates, time zone, publication destination, and any recipients before submission |
| Submission | Validate identity and inputs, then create a `Pending` request |
| Approval | Require human approval for `PTO`; use the configured no-approval path for the other supported types |
| Publication | Create the mapped SharePoint item and an Outlook event through an authorized connection |
| Outcome | Record the final result; do not equate request acceptance with successful publication |

### Baseline Routing

| RequestType | Approval in the reference lab | SharePoint destination |
|---|---|---|
| `PTO` | Required | `TeamCalendar` |
| `OOO` | Not required | `TeamCalendar` |
| `Event` | Not required | `EventCalendar` |
| `Company` | Not required, but caller authorization is still required | `CompanyCalendar` |

These are **lab rules, not a recommended universal business policy**. The owner
must approve the routing and approval matrix before deployment. A company-wide
event is not authorized merely because a user selected `Company`.

## Business Outcomes

| Outcome | Measurement to establish during the pilot |
|---|---|
| Less manual re-entry | Requests completed without manual calendar copying |
| Clearer accountability | Requests with a recorded decision, approver where applicable, and publication result |
| Reliable calendars | Duplicate and partial-publication incidents |
| Better employee experience | Completion rate and time from submission to final result |

Establish measured savings and success rates for each deployment; this runbook
does not publish customer-specific outcome metrics.

## Scope and Boundaries

**In scope:** authenticated single-tenant intake, four request types, PTO
approval/rejection, SharePoint calendar views, explicitly authorized Outlook
publication, and a repeatable acceptance plan.

**Out of scope:** room booking, availability optimization, recurring events,
leave-balance calculations, payroll/HRIS writes, automatic rescheduling,
cross-tenant access, and edits or cancellations of existing events. All-day
events require the explicit extension described in the runbook.

The requestor's email address does not cause the Outlook connector to impersonate
that person. An invitation is also not a direct write into that person's calendar.
Private notes must not be copied into shared calendar entries or invitation bodies.

## Delivery Roles

| Role | Accountability |
|---|---|
| Business owner | Approve request types, approval policy, publication audiences, and pilot outcomes |
| SharePoint owner | Provision lists, views, permissions, and retention |
| Power Platform maker | Build flows and agent tooling; configure connection references |
| Approver | Make the human decision for requests requiring approval |
| Operations owner | Reconcile partial writes, review failures, and maintain connections |

## What This Runbook Provides

The four documents describe the scenario, target architecture, build sequence,
and prompts with expected behavior. The resources folder contains synthetic
acceptance cases and the source lab's license notice.

This folder contains implementation guidance rather than an importable Power
Platform solution, agent export, or live tenant. Configure identity enforcement,
idempotency, publication recovery, and monitoring for the target environment;
retain its acceptance evidence outside this public repository.
