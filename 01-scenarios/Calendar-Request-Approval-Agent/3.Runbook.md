# Calendar Request Approval Agent - Runbook

**Audience:** Delivery engineer and operations owner.
**Status:** Available. Use the acceptance cases below when configuring and
validating the solution in each target tenant.

## Prerequisites

| Requirement | Confirm before building |
|---|---|
| Microsoft 365 | SharePoint Online and Exchange Online available in the target tenant |
| SharePoint | An approved lab site and an owner able to provision lists and permissions |
| Power Platform | An approved environment, maker access, connector/DLP policy, and suitable licensing |
| Copilot Studio | Authoring and runtime entitlement for the intended authenticated channel |
| Connections | Named owners for SharePoint, Approvals, and Outlook connections |
| Calendar access | The Outlook connection can create events in the designated test calendar |
| Test identities | Requestor, approver, and a caller without company-publication permission |
| Business policy | Approved request/approval matrix and publication audiences |

Do not assume premium licensing is either always necessary or always sufficient;
verify the actual connectors and licensing model. Azure infrastructure and a
custom app registration are not prerequisites for the basic connector-based lab.

## Phase 1: Agree the Contract and Provision Lists

1. Review the [architecture contract](./2.Architecture.md) with the business owner.
2. Create `CalendarRequests`, `TeamCalendar`, `EventCalendar`, and `CompanyCalendar`
   in an approved lab site. Add the columns specified in the architecture.
3. Set `Status` to default to `Pending`; require the request type, subject,
   requestor, and both timestamps.
4. Create calendar views for each destination using `StartTime` and `EndTime`.
5. Configure request visibility separately from shared-calendar visibility.
   Ordinary users must not overwrite workflow-owned status or approval data.
6. Record site/list identifiers, connection references, approver configuration,
   and the permitted Outlook calendar in environment-specific configuration.
   Keep real values outside this public runbook.

**Exit criterion:** each connection can perform only its intended operation in
the test environment; a normal requestor cannot alter another person's request.

## Phase 2: Create the Submission Tool

1. In Copilot Studio, create an agent flow with **When an agent calls the flow**
   and **Respond to the agent**. Add the fields described in the architecture.
2. Bind requestor identity through the supported authenticated integration.
   Do not trust a free-form email input, a prompt variable supplied by the model,
   or the flow owner's identity as a substitute for the caller.
3. Validate the type allowlist, subject, timestamps, and authorization for the
   selected request type. Reject a missing caller or unsupported type explicitly.
4. Resolve the user's local dates and time zone, confirm them, and pass normalized
   UTC timestamps. Reject an end that is not after the start. Do not silently
   resolve a daylight-saving ambiguity.
5. Use SharePoint **Create item** to persist the request, generate `Title` from
   the type and confirmed subject, bind the Person field, and set `Pending`.
6. Return the request ID and stored status. Do not claim approval or publication.

Keep the flow's response synchronous and within the platform's agent action
limit. Human approval belongs in a separate automated flow.

The original public lab describes a manual-trigger flow. That recipe is not an
agent-tool export. Use the current
[agent-flow trigger and response requirements](https://learn.microsoft.com/en-us/microsoft-copilot-studio/advanced-flow-create)
when connecting it to Copilot Studio.

For a production implementation, add a unique submission key and atomic
deduplication before retries are enabled. A successful create followed by a lost
tool response must not create a second request on retry.

## Phase 3: Build Approval and Calendar Publication

1. Create an automated flow named `CalendarRequestApproval`, triggered by
   **When an item is created** in `CalendarRequests`.
2. Validate the stored request and its trusted authorization context. Do not
   treat arbitrary direct list inserts as already authorized.
3. For `PTO`, start **Approve/Reject - First to respond** using the configured
   approver. A missing approver, timeout, or failed approval action is an
   operational failure, not permission to auto-approve.
4. On an explicit rejection, update `Status = Rejected`, retain the decision
   comment in the protected request, and terminate without calendar writes.
5. On approval, or on the authorized `OOO`, `Event`, or `Company` path, use a
   Switch to select the destination in the routing table. Make unsupported values
   terminate as failed, never fall through to a default calendar.
6. Create the destination item using the architecture's exact mappings.
7. Create the Outlook event using **Create event (V4)** in the configured
   accessible calendar. Use the confirmed subject and correctly mapped UTC
   timestamps/time zone. Do not derive recipients from `Notes`.
8. After both writes succeed, set `Status = Approved`. For the no-approval branch,
   use a workflow note such as `No approval required by configured policy`;
   do not falsely identify a human approver.
9. Configure failure and timeout handling with correlation to the request ID.
   Alert the operations owner and retain partial-write information.

Do not advertise a successful calendar entry merely because the flow started or
an approval card was accepted. If inviting a requestor is part of the approved
design, obtain confirmation of that outward notification during intake.

## Phase 4: Configure the Agent

1. Require authentication on the intended channel.
2. Add a request topic with the four allowed types, subject, start, end, and
   optional notes. Resolve relative dates against the session date and user's
   time zone.
3. Add an explicit confirmation step showing absolute dates, time zone,
   publication-safe title, destination, and any invitation recipients.
4. Bind the submission flow as the sole write tool. Do not expose direct
   SharePoint or Outlook writes as alternate paths.
5. Use the instructions and prompts in [Sample prompts](./4.Sample-prompts.md).
6. Report submission separately from approval and publication. Do not promise
   a final notification unless a notification action is actually implemented.
7. Keep lookup, update, and cancellation out of scope until dedicated authorized
   tools have been designed. Refer the user to the permitted request view.

## Phase 5: Run Acceptance

Start with [synthetic cases](./0.Resources/acceptance-cases.json). They describe
inputs and expectations, not a flow import or evidence of passed tests. Use a
dedicated test calendar; an Outlook create can notify attendees.

| Case | Expected outcome | Gate |
|---|---|---|
| Confirmed PTO, approver accepts | One request, one TeamCalendar item, one Outlook event; final Approved | Baseline |
| Confirmed PTO, approver rejects | Rejected request; no destination item or Outlook event | Baseline |
| Confirmed OOO | No human approval; TeamCalendar and Outlook publication | Baseline |
| Confirmed Event | EventCalendar, not TeamCalendar or CompanyCalendar | Baseline |
| Company request, authorized caller | CompanyCalendar and configured Outlook calendar | Authorization |
| Company request, unauthorized caller | Explicit denial; no request or calendar publication | Authorization |
| Cancel before confirmation | No tool call and no persisted request | Baseline |
| Missing end, ambiguous zone, unsupported type | Clarify or reject; no premature submission | Baseline |
| Requestor identity spoofing or direct list tampering | Denied at the trusted boundary | Authorization |
| Approval timeout or missing approver | Alert/processing failure; no calendar writes | Recovery |
| Duplicate trigger or lost submission response | No duplicate request or calendar events | Required idempotency extension |
| SharePoint succeeds, Outlook fails or times out | Partial state retained; reconcile before retry | Required recovery extension |
| Private notes in request | Absent from shared calendar/invitation unless explicitly approved | Privacy |
| Daylight-saving transition | Confirmed instants match both published destinations | Date handling |

Record request ID, expected result, actual result, identity role, evidence
location, and pass/fail in a protected test record. Do not add real user data or
screenshots to the repository.

## Phase 6: Release and Operate

Before production, implement the protected processing record and atomic
duplicate controls from the architecture. Verify both baseline and extension
gates, ownership, monitoring, connection lifecycle, and recovery procedures.
Document the approval matrix and obtain business-owner acceptance.

Package flows and agent configuration in a solution with connection references
and environment variables. Provision SharePoint lists separately with a reviewed,
repeatable procedure. This folder does not contain an exported solution.

Monitor pending-request age, approval failures, publication failures, duplicate
detection, and connection expiry. Keep approval data and published calendar data
under separate retention/access policies.

| Symptom | Investigation and response |
|---|---|
| No request ID returned | Inspect submission validation and SharePoint write before retrying |
| Request remains Pending | Inspect approval and publication actions; determine whether any write already succeeded |
| Outlook 403 or wrong calendar | Check the connection identity, delegation, and configured calendar ID |
| Duplicate item or event | Stop blind retries; reconcile by request key and stored destination identifiers |
| Dates shift | Compare original zone, UTC normalization, and connector time-zone mapping |

## Extensions and Cleanup

All-day events require an explicit `IsAllDay`/time-zone contract and exclusive
end-date handling in Outlook. Recurrence, status lookup, cancellation, and edits
need separate authorization, identifiers, and tests; they are not implied by
this baseline.

For rollback, disable intake and pause processing before investigating queued
requests. Disabling the agent does not cancel active approval flows. Reconcile
already-written events before deleting anything. During lab cleanup, remove
only the requests, list items, test events, connections, and resources created
for this lab; retain required audit evidence.
