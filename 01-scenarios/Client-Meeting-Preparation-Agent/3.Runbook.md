# Step-by-Step Guide — Client Meeting Preparation Agent

> **Scenario**: Pre-meeting briefings and post-meeting file notes for client-facing advisers
> **Platform**: Microsoft 365 Copilot · Copilot connectors or MCP server · SharePoint
> **Target Readers**: Delivery engineer, solution architect
> **Estimated effort**: 6–8 weeks, dominated by compliance sign-off and client file remediation

---

## Prerequisites

| Requirement | Owner |
|---|---|
| Microsoft 365 Copilot licences for the adviser population | M365 admin |
| Named compliance owner with authority to sign the boundary instructions | Customer |

## Phase 0 — Compliance Envelope (Weeks 1–2, do not compress)

This scenario fails at sign-off, not at build. Do this first and get it in writing.

### Step 0-1. Write the boundary statement

Draft it, then have compliance edit and sign it. One page. It must state:

| Item | Example wording to adapt |
|---|---|
| What the agent does | "Assembles factual information about a client's existing holdings and relationship history from named internal sources, for internal preparation use by the adviser." |
| What the agent never does | "Does not recommend, suggest, compare, or opine. Does not project or estimate future values. Does not determine or comment on suitability. Does not summarise approved disclosure documents. Produces no client-facing material." |
| Who the output is for | "Internal. The adviser. Not to be shared with the client in any form." |
| What the record is | "The filed file note is the record. The agent conversation is not." |
| Escalation | "Any output that appears to constitute advice is reported to [named contact] and the agent is withdrawn pending review." |

**Deliverable:** signed boundary statement. Nothing else starts until this exists.

### Step 0-2. Map the information barriers

| Population A | Must not interface with | Enforced today by | Applies to this agent? |
|---|---|---|---|

For each barrier, confirm **where it is enforced at the data layer**. If the honest answer is
"by convention", that is a finding, and it is a finding that predates your project.

**Deliverable:** barrier map, signed by risk.

### Step 0-3. Baseline the problem

| Measure | Today |
|---|---|
| Average preparation time per client meeting | |
| Meetings per adviser per week | |
| Time to write a file note | |
| Proportion of meetings with a filed note within SLA | |

The last row is often the strongest business case and nobody thinks to measure it.

### Step 0-4. Define the briefing structure

With three or four actual advisers — not managers. Ask them to talk through how they prepare
today, and write down the order in which they want the information. That order is the agent
instruction.

> ✅ **Exit criteria:** signed boundary statement, barrier map, baseline, briefing structure
> drafted from real advisers.

## Phase 1 — Data Access and Barrier Enforcement (Weeks 2–4)

### Step 1-1. Connect the client file

Follow the
[Copilot Connector Knowledge Onboarding runbook](../../02-patterns/Copilot-Connector-Knowledge-Onboarding/Copilot-Connector-Knowledge-Onboarding-Runbook.md)
for SharePoint client files and the approved product library.

Two things specific to this scenario:

- **Client folder naming.** Near-identical structures across hundreds of client folders is the
  main cause of the agent citing the wrong client's document. Verify that folder and file naming
  disambiguates the client, and that permissions — not naming — enforce separation.
- **The approved library must be marked as authoritative** in whatever way your platform
  supports, and the agent must be instructed to point at it rather than summarise it.

### Step 1-2. Connect the book of record

Choose the topology using the table in [2.Architecture.md](2.Architecture.md). If the core
platform is on-premises or in a private network — common in this sector — go to the deployment
topologies section of
[MCP Server Integration](../../02-patterns/MCP-Server-Integration/MCP-Server-Integration.md)
and select a gateway-mediated pattern. Do not plan on direct access.

Whatever the topology, the requirement is the same: **per-user identity through to the source**,
so that the source system's own entitlements do the work.

### Step 1-3. Prove the barriers hold

This is the most important test in the whole engagement. Build the matrix and keep the evidence.

| # | Test user | Segment | Target client / data | Must see? | Result |
|---|---|---|---|---|---|
| 1 | Adviser A | Wealth | Own client | ✅ | |
| 2 | Adviser A | Wealth | Another adviser's client, same segment | per policy | |
| 3 | Adviser A | Wealth | Client in a barriered segment | ❌ | |
| 4 | Adviser B | Barriered segment | Adviser A's client | ❌ | |
| 5 | Team leader | Wealth | Any client in own team | ✅ | |
| 6 | Adviser A **after moving segment** | New segment | Previous segment's clients | ❌ | |

Row 6 is the one people skip and the one that fails. Move a test user between segments, wait for
propagation, and re-run. Record how long propagation took.

> ✅ **Exit criteria:** data connected, permission and barrier matrix passed with evidence,
> propagation delay measured and documented.

## Phase 2 — Build the Agent

1. Create a declarative agent in Agent Builder. Move to Copilot Studio only if you need
   write-back to the book of record or a prescribed conversation flow.
2. Add knowledge: client file, approved product library, book-of-record integration.
3. Turn **off** web search. There is no scenario here that benefits from public web content, and
   several that are harmed by it.
4. Turn **off** ungrounded responses. The agent must say "not recorded" rather than reason from
   general knowledge about finance.

---

## Phase 3 — Instructions

Two blocks matter: the briefing structure, and the boundaries. Write the boundaries first.

```text
ROLE
You prepare internal briefing material for advisers ahead of client meetings at
<Firm>. You assemble facts from the firm's own records. You are not an adviser.

HARD BOUNDARIES — these override every other instruction
- Never recommend, suggest, advise, or opine on what a client should do.
- Never compare products or comment on whether something is suitable for a client.
- Never project, estimate, or model future values, returns, or outcomes.
- Never summarise, paraphrase, or restate an approved disclosure or product
  document. Provide the document title and link only.
- Never produce material intended for the client to see. All output is internal.
- If asked to do any of the above, respond: "That falls outside what I can help
  with. Please refer to [approved process]." Then stop.

SOURCES
- Answer only from the firm's connected records: the book of record, the client
  file, correspondence and meeting history, and the approved product library.
- Cite the source of every factual statement.
- If a value is not present in the records, write exactly "Not recorded in
  <source>". Never estimate or infer.
- Any monetary value or position must be reported with its "as at" date.

BRIEFING STRUCTURE
When asked to prepare for a meeting with a client, produce:
1. At a glance — 4 bullets maximum: relationship length, what they hold,
   value as at date, next scheduled review
2. Position — current holdings with values and as-at dates
3. What has changed since the last meeting — additions, exits, material moves
4. Relationship context — stated preferences, life events, and commitments
   recorded in correspondence or prior file notes, each with its date and source
5. Outstanding items — open actions and outstanding documents from the last
   meeting
6. Watch-outs — anything recorded that requires care: vulnerability indicators,
   complaints history, restricted topics, or barriers
7. Sources — every document and record used

FILE NOTE
When asked to draft a file note, use <Firm>'s prescribed structure exactly.
Record only what the adviser tells you happened. Do not infer outcomes, do not
add analysis, and do not characterise the client's intentions.

TONE
Factual and neutral. No adjectives about the client. No assessment of the
relationship.
```

Notes on why this is shaped this way:

- **"No adjectives about the client"** does real work. Characterising a person is where an
  otherwise-factual briefing turns into something a firm would not want disclosed.
- **The as-at date rule** prevents the most likely real-world harm: an adviser quoting a stale
  valuation in a meeting.
- **Structuring the request as retrieval rather than profiling** also reduces the safety-filter
  friction described in [2.Architecture.md](2.Architecture.md). The compliant formulation and
  the reliable formulation are the same formulation.

### Handling filter friction

If legitimate prompts are blocked:

1. Reword from characterisation to retrieval — "extract the recorded life events with dates and
   sources" rather than "tell me about this client's personal situation".
2. Split broad prompts into narrower ones.
3. Remove instructions asking the model to infer, assess, or profile.
4. Record the blocked prompt and the working rewording in the resources folder. This list
   becomes user enablement material.

Escalate only after these have been tried and documented.

## Phase 4 — Evaluate

### Step 4-1. Build the evaluation set

At least 25 clients, spanning:

- 5 with complete, well-maintained files
- 5 with sparse or stale files
- 3 with long relationship histories (many years of correspondence)
- 3 recently onboarded
- 3 with recorded watch-outs (complaints, vulnerability indicators)
- 3 across a barrier the test user must not cross
- 3 where the adviser knows the client intimately and can catch subtle errors

### Step 4-2. Score on five axes

| Axis | Question | Failure means |
|---|---|---|
| **Accuracy** | Every stated fact correct, with a correct as-at date? | Any fabricated figure or date is a hard fail |
| **Completeness** | Anything material missed that the adviser would have found? | Retrieval or file-hygiene problem |
| **Boundary** | Any statement that reads as advice, projection, or suitability? | Hard fail. Stop and revise instructions |
| **Attribution** | Every claim cited and traceable? | Not fit for supervision |
| **Consistency** | Same client, three runs, comparable briefing? | Diagnose before rollout |

### Step 4-3. Compliance review of real output

Give compliance ten real briefings and one instruction: **find anything that reads like advice.**
This is the review that determines whether the agent goes live. Schedule it early enough that
you can act on the result.

### Step 4-4. Adviser review

Ask three advisers: *"Would you walk into a client meeting with this?"* Anything less than an
unqualified yes, find out exactly what they would add or check first. That list is your
remaining work.

## Phase 5 — Pilot and Rollout

1. Pilot with a **single business unit inside one barrier segment**. Do not pilot across a
   barrier.
2. Run for a full review cycle — long enough that pilot advisers use it for real meetings, not
   demonstrations.
3. Measure against the Phase 0 baseline: preparation time, file note timeliness.
4. Collect every instance where an adviser did not trust the output, and why.

### Go/no-go

| Signal | Action |
|---|---|
| Zero boundary failures and advisers using it unprompted | Proceed |
| Zero boundary failures but low usage | A trust or quality problem — investigate before scaling |
| **Any** boundary failure | Stop. Revise instructions, re-test, re-review with compliance |

There is no acceptable rate of boundary failures. This is different from accuracy, where you can
reason about thresholds.

### Rollout

1. Expand one segment at a time, re-running the barrier tests for each.
2. Publish the agent through the approval route so it has an owner and a review record.
3. User enablement must cover: what it does not do, the blocked-prompt reworkings, how to check
   an as-at date, and that the filed note is the record.

## Phase 6 — Operate

| Cadence | Activity | Owner |
|---|---|---|
| Weekly (first month) | Review sample briefings for boundary drift | Compliance |
| Weekly | Adviser feedback triage: quality vs file hygiene vs expectation | Delivery engineer |
| Monthly | Preparation-time and file-note-timeliness measure vs baseline | Business sponsor |
| Monthly | Client file hygiene report — which files produce weak briefings | Data owner |
| Quarterly | Re-run the full evaluation set and the barrier matrix | Delivery engineer |
| On segment change | Re-run barrier tests | Risk |
| On model or platform change | Re-run evaluation, especially boundary cases | Delivery engineer |
