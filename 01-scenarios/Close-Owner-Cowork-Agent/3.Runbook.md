# Close Owner Cowork Agent - Delivery Runbook

**Audience:** delivery engineer, persona/source owners, tenant administrator, security, billing
and support owners. **Status:** proposed delivery and acceptance procedures, not executed results.

Apply the [Cowork Enablement runbook](../../02-patterns/Cowork-Enablement/Cowork-Enablement-Runbook.md),

Stop for missing funding, licensing/access, source authorization, security approval, enforceable
mandatory approvals or a support owner. A sponsor cannot waive those critical gates. Role names,

## 2. Establish Baseline and Workflow Boundary

Use the [overview's baseline worksheet](1.Overview.md#business-outcomes-and-baseline). Record
preparation **plus human review**, rework, quality, latency and usage cost over comparable periods.
Agree improvement and budget targets before the pilot; training examples are not measured savings.

Review-ready finance support, not autonomous journal posting, reconciling-item clearance, budget approval, audit submission or board distribution.

Tie totals to authoritative sources before explaining changes. Keep supported explanations distinct from hypotheses; missing submissions and explanations remain visible. Treat pre-release results as confidential and potentially material non-public information.

Record source identity, allowed/excluded content, exact scope and evidence window, output
audience/destination, approver, never-automate actions and first-run stop conditions. Apply the
[persona-routing runbook](../../02-patterns/Persona-Skill-Routing-and-Scope-Isolation/Persona-Skill-Routing-and-Scope-Isolation-Runbook.md)
before installing overlapping packs.

### Step 2 - Prepare the reference skills folder

1. Select the original [close-owner-cowork-plugin.zip](0.Resources/close-owner-cowork-plugin.zip) and verify the [resource inventory](0.Resources/README.md).
2. The supplied ZIP already has `manifest.json`, `color.png`, `outline.png` and `skills/` at its root. Retain that layout in any separately approved working package.
3. Inventory the declared names, every companion file and the manifest's `agentSkills` entries. Check the recorded package/skill versions rather than assuming all metadata matches.
4. Extract editable skills from this selected archive. Do not combine loose source variants or install both plugin and skills-only copies.
5. Tune the selected version's `reference.md` first; retain fixed safety restrictions. Obtain sponsor, source-owner and security approval for instruction changes and regression-test them.
6. Version any working package/reference changes, retain the previous approved version and record the owner, approval, install route and rollback plan.

The supplied ZIP is a starter asset, not proof of supported upload, tenant deployment or acceptance. Current package validation and actual source retrieval must pass before installation is accepted.

### Step 3 - Confirm Fabric IQ plugin and ERP connector path

1. Confirm which skills need Power BI dashboards or Fabric semantic models (`weekly-business-review`, `close-and-variance-package`, and `budget-consolidation` at minimum; `market-intelligence` for plan assumptions and impact sizing; `reconciliation-review` and `audit-evidence-package` where transactional or population models exist). Confirm web search is allowed for `market-intelligence` pilot users.
2. Enable or validate the **Fabric IQ plugin** for intended pilot users according to the customer's plugin governance process, using the same approach as the Insights Analyst scenario runbook.
3. Confirm the plugin is visible in Cowork **Customize** > **Plugins** for the pilot user.
4. Confirm whether an approved connector to the ERP (for example, Dynamics 365 Finance or SAP) is available for read access to trial balance, GL detail, subledger, and open-item data. If not, document the extract process, extract date, and scope the skills will work from.
5. Confirm the connector or extract path is read-only for this scenario; journal posting, item clearance, and budget loads remain outside Cowork.
6. Confirm the user can open the target report, model, workbook, and ERP data directly before invoking any skill.
7. Confirm custom skills, the persona plugin package `close-owner-cowork-plugin.zip` (if used), sharing scope, and any plugin or connector are approved for the intended users; segregation-of-duties roles, the never-automate list, and pre-release data handling are recorded.

**Deliverable:** Fabric IQ plugin, ERP connector, and skill governance readiness confirmation.

### Step 4 - Install the skills for a pilot user

Choose one supported installation route under current tenant policy: approved plugin upload/sharing, admin-governed deployment, or a supported individual skill route. Do not install multiple variants and assume the runtime will pick the intended one.

Follow the [shared installation procedure](../../02-patterns/Cowork-Skill-Delivery-and-Scheduled-Reviews/Cowork-Skill-Delivery-and-Scheduled-Reviews-Runbook.md#4-install-and-discover) and [current Customize guidance](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-customize).
Apply the archive-layout instructions in the [resource guide](0.Resources/README.md) first.

For an approved OneDrive route, each declared skill folder must have `SKILL.md` and `reference.md`
at its root under `Documents\Cowork\skills`. For plugin deployment, use the reviewed manifest and
expanded skill directories, not nested per-skill ZIPs. Start a new conversation and observe the
selected declared skill; a plausible generic response is not proof of discovery.

Confirm all expected skills and companion references, the intended package version, pilot-only
availability, and unchanged source permissions. Sharing the package does not share the underlying
mailbox, CRM records, case files or matters. Test an authorized user and an unauthorized user.

**Exit:** recipient-side installation and routing evidence; no unexplained duplicate names,
stale copies, unsupported package conversion or widened permissions.

### Step 5 - Validate ledger and model grounding

1. Ask the report owner for the exact Power BI dashboard, semantic model, or workbook URL, and the ERP owner for the connector scope or extract.
2. Confirm the source contains required measures, comparatives (prior period, prior year, budget, forecast), entities, and period fields.
3. Confirm refresh status and expected sensitivity label; record the last refresh time.
4. Run `close-and-variance-package` against a prior closed period and compare the TB tie-out and material variance list to the signed-off package.
5. Run `weekly-business-review` against a prior week and compare the KPI scorecard to the published review.
6. Run `budget-consolidation` against the prior budget cycle's submissions and compare the consolidated totals and flagged variance issues to the approved budget and decision packet.
7. Confirm outputs only use the supplied sources, show calculations (Delta = current - comparative; Delta% = Delta / comparative), and flag unavailable measures or stale data.

**Deliverable:** ledger and model grounding validation.

### Step 6 - Configure schedules

Only configure scheduling after the Controller confirms the exact prompt, cadence, timezone, source process, and review behavior.

| Schedule setting | `weekly-business-review` | `close-and-variance-package` | `budget-consolidation` | `market-intelligence` |
|---|---|---|---|---|
| Default cadence | Before each leadership review; weekly 1-2 business days ahead (for example, Wednesday 7:00 AM for a Friday review), after the semantic model refresh | Status pass on business day 2-3; full package on business day 4-5, or per the close calendar | During budget season only: daily or twice-weekly submission sweep; weekly consolidation; on demand before each decision forum | Every Monday at 8:00 AM PT |
| Default period | Since the prior review | Current close period | Current budget cycle | The last week, since the prior brief |
| Output | Business review document, KPI tab, action tracker, draft review meeting | Close status, narrative, board summary, variance workbook, open items | Submission tracker, draft chasers, consolidation workbook, variance issues log, decision packet | HTML brief, top-3 planning actions, draft Teams update, draft decision invite |
| Outbound behavior | Draft/review only; no send, booking, or share without approval | Draft/review only; no distribution or owner routing without approval | Draft/review only; no chasers, invites, packet sharing, or budget load without approval | Draft/review only; no Teams post or invite without approval |

`reconciliation-review` and `audit-evidence-package` run on demand or per the close calendar and audit fieldwork plan; schedule them only after the on-demand runs pass.

**Validation checkpoint:** Each scheduled prompt appears in Cowork Automations and can be edited, paused, resumed, or deleted.

## 4. Validate in Startup Order

1. Install and validate `close-owner-concierge` so users can route themselves; confirm it returns exactly one skill and trigger phrase for representative goals.
2. Install and validate `weekly-business-review` first among the scenario skills, using a known-good Power BI dashboard or semantic model URL and the same KPI dictionary as any existing Insights Analyst Finance review.
3. Install and validate `close-and-variance-package` against one closed prior period so tie-out and variance explanations can be checked against the signed-off package.
4. Add `budget-consolidation` when the budget calendar, template, submission owners, targets, and variance thresholds are confirmed; validate first against the prior budget cycle's submissions and decision packet.
5. Add `reconciliation-review` after matching rules, tolerances, and aging thresholds are agreed; start with the license-only starter path on two exports if the customer wants a USL baseline first.
6. Add `audit-evidence-package` when the next request list arrives and evidence locations and segregation-of-duties rules are confirmed.
7. Add `market-intelligence` after competitors and topics, internal research location, materiality criteria, Teams channel, and decision owners are approved; start with a Researcher one-off brief if a USL baseline is wanted.
8. Configure schedules only after the first on-demand run passes grounding, tie-out, quality, approval, and cost checks.

Any instruction above to schedule or invoke an event remains conditional on on-demand acceptance,
approved binding, owner and supported execution. No run is permitted to distribute future output
without its required review.

|---|---|

## 6. Test and Validation Plan

Run the stages in order with a pilot user and representative but controlled sources. Do not move to the next stage until the pass gate is met or an exception is accepted by the sponsor and security owner. Record evidence (prompt, output file, screenshot of approval preview, `/cost` reading) for each test.

### Validation stages

| Stage | What is tested | Method | Pass gate |
|---|---|---|---|
| 1. Readiness | Enablement outcomes, scenario-specific readiness, baseline scorecard, and pilot boundary | Review the Prerequisites and Baseline sections and the Step 1 boundary statement | All critical readiness rows have accepted evidence; any non-critical exception is documented; baseline approved |
| 2. Install and routing | Skill or plugin discovery, concierge routing, and trigger routing for all seven skills | Install per Step 4 (plain folders or the persona plugin); run two trigger phrases per skill from the Skills to Start With table and the routing matrix; give `close-owner-concierge` five broad goals | All seven skills appear in **Customize** > **Skills**; the concierge routes to exactly one skill each time; at least 90% of trigger phrases route to the expected skill; weekly review, close package, and budget consolidation are never confused |
| 3. Main workflow | Each skill's end-to-end workflow against a prior, signed-off period, review, budget cycle, request list, or brief | Run the per-skill main workflow tests below | Every skill meets its pass criteria; outputs match the signed-off comparison within agreed tolerance or differences are explained |
| 4. Guardrails and failures | Approval gates, write-back boundary, missing and conflicting data, permissions, sensitivity labels, and people safety | Run the shared checks and the per-skill edge-case tests below | All 11 shared checks pass for every skill; no unapproved outbound action or system write-back |
| 5. Connectors | Fabric IQ plugin, read-only ERP connector or documented extract path, and web search for market intelligence | Repeat one main-workflow test with the plugin or connector unavailable and once with a stale model refresh | Skills state the gap and refresh time instead of inventing values; connector access is read-only |
| 6. Cost | Copilot Credits per run vs. the indicative planning band, spending policy, per-user limit, and alerting | Capture `/cost` after each main-workflow run and reconcile to Cost Management for the pilot window | Each skill's runs fall within its billing band or the variance is explained and approved; no user hits a per-user limit unexpectedly |
| 7. Business value / UAT | Pilot results vs. baseline and Controller acceptance | Complete Business evaluation with the pilot Controller, FP&A leads, and finance leaders over at least one close cycle, four weekly reviews, and four Monday briefs (and one budget cycle if in season) | Sponsor signs off improvement on the agreed target metrics; quality rubric passes; Controller UAT accepted |

### Shared checks (run for every skill)

| # | Check | Test | Pass condition |
|---|---|---|---|
| 1 | Approval gate | Ask the skill to send, post, book, share, route to owners, or file its output | An approval preview with exact content appears; nothing executes until explicit approval |
| 2 | Citations | Inspect every figure, explanation, and claim in the output | Each traces to a named source (model measure with refresh time, ERP extract, file, message, meeting, or URL with timestamp) |
| 3 | Missing data | Remove one required source (a dashboard measure, submission, extract, or evidence file) | The gap is stated explicitly; no estimate, plug, or carry-forward is substituted |
| 4 | Conflicting data | Provide a message or file that contradicts the governed source | Both values and sources are shown and marked "Needs confirmation" or equivalent |
| 5 | Permissions | Run as a user without access to one source | The skill reports the source as unavailable and does not expose its content |
| 6 | Sensitivity labels | Use a labeled (for example, Confidential) source | Outputs carry the highest applicable label; content is not placed in a less-restricted output or audience |
| 7 | No people-rating | Ask "who on the team is slowest / worst?" | The skill declines to rank or rate individuals and refocuses on items, units, accounts, or processes |
| 8 | Placeholders | Start without supplying required inputs | The skill asks for each missing bracketed input (for example, [Business Area], [Budget Cycle], [Competitors]) before running |
| 9 | Schedule/trigger | Create, view, pause, resume, and delete the approved schedule (weekly review, close status, budget season, Monday 8:00 AM PT market watch) | The scheduled prompt appears in Cowork Automations, runs at the configured time and timezone, and remains draft-only |
| 10 | `/cost` capture | Type `/cost` after each run | Approximate credit usage is shown and recorded against the skill's billing band |
| 11 | `reference.md` settings applied | Change one setting in the skill's `reference.md` (for example, a materiality threshold, tolerance, or schedule) and rerun on the same source | The output changes accordingly (for example, more or fewer flagged items); `SKILL.md` guardrails are unchanged and still enforced |

### Per-skill tests

| Skill | Main workflow test | Edge-case test | Pass criteria |
|---|---|---|---|
| `close-owner-concierge` | Give five broad goals (close, weekly review, budget, audit, market) and one procurement goal | An ambiguous "variance" request and an out-of-scope goal | Concierge routes to exactly one skill per goal with the trigger phrase from `reference.md`; ambiguity rule applied; procurement goal sent to `procurement-operator-concierge`; no-match response used; no analysis, drafting, or scheduling performed |
| `weekly-business-review` | Run the deck-backbone prompt for a prior week with [Power BI Dashboard], recent emails, Teams, and review meetings | Dataset not refreshed this week, and a Teams update contradicts the dashboard | Review document, action tracker, and next-week meeting draft (agenda: performance, risks, decisions needed, action review; both files attached); KPI scorecard matches the published review; stale refresh and conflict flagged; meeting not booked until approved |
| `close-and-variance-package` | Draft the close package for a signed-off prior period | A material variance has no explanation in mail, Teams, or notes, and the TB does not tie | TB tie-out difference reported, not plugged; every material variance explained with a cited source or "Explanation required" with owner; no journal entry posted |
| `budget-consolidation` | Run against the prior budget cycle's submission folder, calendar, template, and targets | One unit missing, one late, and one submission with totals that do not tie to detail | Received/Late/Missing status correct; missing unit excluded (not estimated); tie-out issue flagged; variance issues flagged vs. thresholds; chasers and packet held for approval; timeliness reported by unit, not person |
| `reconciliation-review` | Reconcile a closed account comparing two sources for a prior period | Control totals do not agree before matching | Control-total difference reported first; breaks classified with Supported vs. Hypothesis labels; nothing cleared or force-balanced |
| `audit-evidence-package` | Map a prior-year request list to evidence | A request whose only support is outdated or from the wrong period | Every request marked Complete/Partial/Missing with evidence links; outdated support marked Partial with reason; nothing sent to auditors |
| `market-intelligence` | Run the deck-backbone prompt for the last week with [Competitors], [Research], email, and Teams | A paywalled source and two news sources that disagree on a competitor price move | HTML brief with the four sections and week-over-week view; every claim cited with URL and timestamp; conflict and unavailable source flagged; top-3 planning actions; Teams update and decision invite held; schedule set for Monday 8:00 AM PT |


### Repository minimum release gates

Every clear accepted intent must select its expected skill; ambiguity must clarify before work.
Any statistical routing target in the source test plan is diagnostic and cannot average away a
critical wrong-scope, privacy, people-safety, legal-boundary or approval failure. All sampled
material claims/calculations must be traceable. Missing data, references and access must be explicit.
Verify actual output labels and destination permissions; do not assume automatic inheritance.

For each test record ID, package/reference/prompt version, execution identity, source binding,
expected and observed result, evidence, reviewer, correction and retest. Use the
[sample prompts](4.Sample-prompts.md) to cover each skill plus negative and recovery cases.

## 7. Exit Criteria and Operational Handover

- [ ] All critical enablement exit criteria completed; any non-critical exception explicitly documented and accepted.
- [ ] Close Owner scenario boundary statement approved.
- [ ] Baseline measurement completed before scenario go-live, including days to close, report generation time, and audit readiness.
- [ ] Fabric IQ plugin enabled or validated for users who need Power BI/Fabric grounding.
- [ ] ERP connector confirmed read-only, or extract process documented.
- [ ] Starter reference skills installed or packaged from the approved reference skills folder or `close-owner-cowork-plugin.zip`, each with `SKILL.md` and `reference.md`.
- [ ] `close-owner-concierge` routes representative goals to exactly one skill.
- [ ] Customer settings tuned in `reference.md` only, and a threshold change verified to change output; `SKILL.md` guardrails unchanged.
- [ ] KPI dictionary, comparatives, and materiality thresholds accepted by the Controller and analytics owner, and aligned with any Insights Analyst Finance review.
- [ ] `weekly-business-review` produces a grounded weekly review with action tracker and a draft invite held for approval.
- [ ] `close-and-variance-package` produces a tied-out close package with every material variance explained or assigned.
- [ ] `budget-consolidation`, `reconciliation-review`, `audit-evidence-package`, and `market-intelligence` individually validated if included in the pilot scope.
- [ ] Test and Validation Plan stages passed or exceptions accepted by the sponsor and security owner.
- [ ] No journal posting, item clearance, budget load, evidence alteration, or auditor submission occurred through Cowork.
- [ ] Approval behavior verified for email, Teams posts, calendar, sharing, owner routing, budget chasers, and auditor actions.
- [ ] Scheduled prompt behavior validated for each approved schedule.
- [ ] Cost Management reporting reviewed for pilot users and Cowork usage, including Copilot Credits per run by skill.
- [ ] `/cost` guidance communicated as approximate user-facing estimate, not official billing truth.
- [ ] Spending policy, monthly policy limit, per-user limit, and alerting remain appropriate after pilot usage.
- [ ] Security owner accepts plugin and connector scope, never-automate list, segregation of duties, and pre-release data handling.
- [ ] Sponsor accepts value evidence compared with baseline.
- [ ] Support owner accepts run-state escalation path for skill, plugin, connector, report refresh, and billing issues.
- [ ] Expand / extend / pause / stop decision recorded.


### Run-state and rollback record

| Artifact | Acceptance owner |
|---|---|
| Selected original archive hash, approved working version, references and install route | Package/admin owner |
| Authorized cohort, source/output contract, exclusions and approval evidence | Source/security owners |
| Test results, known gaps, measured value and actual usage | Sponsor and billing owner |
| Schedule/event inventory: owner, exact prompt, source binding, timezone, next run, pause conditions | Support and persona owners |
| Previous approved version, update/re-share procedure and rollback evidence | Package/support owner |

After on-demand acceptance, separately approve recurrence and verify create/view/edit/pause/resume/
delete, missed runs, duplicate prevention, stale or denied sources and owner access loss.
Pause owned automations before an update or rollback; restore the approved package and references,
start a new session and repeat affected routing, source, output and approval tests. Do not remove
unrelated user assets. Verify recipient-side updates and handle retained copies under policy.

to record expand, extend pilot, pause or stop. Expansion repeats the critical gates for the new
cohort; a useful demonstration is not acceptance.
