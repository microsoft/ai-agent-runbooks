# Step-by-Step Guide — Copilot Licence Lifecycle Agent

> **Scenario**: Conversational management of the Microsoft 365 Copilot licence estate
> **Platform**: Microsoft Copilot Studio · Power Platform · Microsoft Graph
> **Target Readers**: Delivery engineer
> **Estimated effort**: 1–2 weeks

---

## Prerequisites

| Requirement | Details |
|---|---|
| Power Platform environment | Non-default, Dataverse enabled, Managed Environment recommended |
| Copilot Studio licence / capacity | Plus allocated Copilot Credits for the dev environment |
| Graph permissions | Read users and subscribed SKUs, read Copilot usage reports, write licence assignment |
| Service identity | Dedicated, owned, documented — not an individual's admin account |
| Business agreement | Dormancy definition, grace period, and approval model signed off |

---

## Phase 0 — Agree the Rules Before Building

This agent takes actions that affect people's tools. Get written agreement on:

| Question | Record the answer |
|---|---|
| What is "dormant"? | e.g. no Copilot activity for 45 consecutive days |
| Who is excluded? | e.g. approved leave, executive assistants, a named exclusion group |
| How long is the grace period? | e.g. 14 days, with notifications on day 0 and day 10 |
| Is reclaim automatic or approved? | Start with approved |
| Who approves? | Named role, with a backup |
| Who can invoke action topics? | A specific security group |
| What is the escalation route for a disputed reclaim? | Named contact |

> ⚠️ Skipping this phase produces an agent that works perfectly and gets switched off in week
> two after the first angry escalation.

---

## Phase 1 — Environment and Solution Setup

1. **Power Platform admin center → Environments → New**. Type: Production (or Sandbox for dev).
   Enable Dataverse. Do **not** use the default environment.
2. Allocate Copilot Credits to this environment explicitly, so development and testing draw
   against a bounded pool rather than the tenant capacity.
3. Create an unmanaged **solution** and build every component inside it from this point on.
4. Create environment variables:
   - `DormancyDays` (default 45)
   - `GracePeriodDays` (default 14)
   - `AutoReclaimEnabled` (default `false`)
   - `LicenceAdminGroupId`
   - `ExclusionGroupId`
5. Create connection references for Microsoft Graph, Office 365 Outlook, and Microsoft Teams.

---

## Phase 2 — Data Model

Create the Dataverse tables described in [2.Architecture.md](2.Architecture.md):
`LicenceHolder`, `WaitlistEntry`, `ReclaimCase`, `Configuration`, `AuditEvent`.

Guidance:

- Give `ReclaimCase` a proper status column (`Detected`, `Notified`, `Cancelled`, `Reclaimed`,
  `Disputed`) rather than booleans. You will need to report on it.
- Put a lookup from `AuditEvent` to `ReclaimCase` so the trail is navigable.
- Add an alternate key on `LicenceHolder.UserId` so upserts from the sync flow are idempotent.

---

## Phase 3 — Build the Agent Flows

Build the flows before the agent. They are the part that can fail in interesting ways, and it is
easier to test them standalone.

### Flow 1 — Sync licence inventory (scheduled, daily)

1. Query Graph for users with a Microsoft 365 Copilot licence.
2. Query the Copilot usage report for last-activity signals.
3. Upsert into `LicenceHolder`.
4. Write a summary `AuditEvent`.

### Flow 2 — Detect dormancy (scheduled, weekly)

1. Read `DormancyDays` from configuration.
2. Select `LicenceHolder` rows past the threshold, excluding members of `ExclusionGroupId`.
3. Create a `ReclaimCase` with status `Detected` for each.
4. Do **not** notify from this flow. Detection and notification should be separable so you can
   run detection in report-only mode during the pilot.

### Flow 3 — Notify (triggered by agent or schedule)

1. Send a Teams message and an email to the user, stating the grace period end date and how to
   keep the licence.
2. Update the `ReclaimCase` to `Notified` with `GraceEndsOn`.

### Flow 4 — Reclaim

1. Confirm the `ReclaimCase` is `Notified` and past `GraceEndsOn`.
2. Confirm the user is still dormant — re-check, do not trust the stale record.
3. Remove the licence via Graph.
4. Update the case to `Reclaimed`, write an `AuditEvent` naming the approving human.

### Flow 5 — Assign from waitlist

1. Take the top `WaitlistEntry` by position.
2. Assign the licence via Graph.
3. Notify the user, update the entry, write an `AuditEvent`.

### Test each flow standalone

Run each against a test user before wiring it into the agent. A flow that fails inside an agent
conversation is far harder to diagnose than one that fails in the flow designer.

## Phase 4 — Build the Agent

1. Create the agent in Copilot Studio, inside your solution.
2. **Separate read from write.** Create two clear groups of topics:
   - **Reporting topics** — inventory, usage, waitlist status, dormancy report. Safe to run
     freely.
   - **Action topics** — notify, reclaim, assign. Each must include an explicit confirmation
     step that restates what will happen, to whom, and asks for a yes.
3. Configure end-user authentication so actions attribute correctly.
4. Agent instructions:

```text
ROLE
You help the licence management team administer Microsoft 365 Copilot licences.

BEHAVIOUR
- For questions, answer from the licence data. Always state the "as of" date
  of the data you are reporting.
- For actions (notify, reclaim, assign), always summarise exactly what will
  happen — which user, which licence, which effective date — and ask for
  explicit confirmation before proceeding. Never take an action on an
  ambiguous instruction.
- Never take an action on more than 25 users in a single request. If asked to
  do more, propose splitting it and ask for confirmation.

BOUNDARIES
- Do not speculate about why a user is inactive.
- Do not discuss individual users' activity with anyone outside the licence
  management team.
- If a user disputes a reclaim, record it and route to the named escalation
  contact. Do not reverse a decision on your own.

FORMAT
- Reports as tables.
- Actions as a confirmation summary, then a result summary.
```

The 25-user batch limit exists because a single mis-parsed instruction should not be able to
strip licences from a whole department.

## Phase 5 — Test

### Functional tests

| Test | Expected |
|---|---|
| Ask for the current licence inventory | Table with counts by department and an "as of" date |
| Ask who is dormant | List, with last activity date and days dormant |
| Ask to reclaim a specific test user | Confirmation prompt first, then the action |
| Confirm the reclaim | Licence removed, case updated, audit event written |
| Ask to reclaim 200 users | Refuses, proposes splitting |
| Ask an ambiguous question ("clean up the dormant ones") | Asks for clarification, does not act |

### Attribution test

Run a reclaim as a non-maker member of the licence admin group, then inspect the `AuditEvent`.
It must name **that person**, not the maker or the service identity alone. If it does not, the
connection is configured with maker credentials — fix it before go-live.

### Cost test

Record the credits consumed by a full test cycle. Extrapolate to the expected monthly
interaction volume. If the number is uncomfortable, reduce generative orchestration in the
reporting topics — deterministic topics are cheaper than generative answers.

---

## Phase 6 — Pilot and Rollout

1. Run **detection in report-only mode** for one full cycle. Compare the dormancy list against
   what the licence team believes to be true. Expect discrepancies — people on leave, shared
   mailboxes, service accounts. Refine the exclusion group.
2. Run one notification cycle with a small group. Measure how many users respond by using
   Copilot again — that reactivation is itself a good adoption outcome and worth reporting.
3. Enable reclaim with approval. Keep `AutoReclaimEnabled` false.
4. Only consider automatic reclaim after three clean cycles.

---

## Phase 7 — Handover

This agent works well as an enablement asset. When handing over:

1. Walk the customer team through the solution structure, not just the UI.
2. Show them how the environment variables change behaviour without a rebuild.
3. Show the separation between reporting and action topics and explain why it exists.
4. Hand over the ALM pipeline, not just the agent.
