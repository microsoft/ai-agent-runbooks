# Step-by-Step Guide — Document Processing & Extraction Agent

> **Platform**: Foundry / Document Intelligence · Content Understanding · Copilot Studio · Power Automate
> **Target Readers**: Delivery engineer, solution architect
> **Estimated effort**: 6–10 weeks per document type family

---

## Prerequisites

| Requirement | Owner |
|---|---|
| 100+ **real** documents, including the bad ones | Customer |
| Golden set: 30+ documents with independently confirmed correct values | Customer process owner |
| Master data access for validation | Customer data owner |
| Foundry / Document Intelligence resource in the correct region | Platform team |
| Downstream boundary confirmed in writing | Integration owner |
| Named process owner who can set the acceptable error rate | Customer |

## Phase 0 — Qualify (Week 1)

### Step 0-1. Get real documents

Not samples. Not the clean ones. Ask specifically for:

- the worst scan anyone has seen this month
- a photographed document
- a multi-page attachment containing more than one document
- one in each language in scope
- one with a large line-item table
- one that a person got wrong last quarter

### Step 0-2. Answer the four questions that set the architecture

| Question | Answer | Consequence |
|---|---|---|
| Scanned or native? | | Foundry vs Copilot Studio |
| How many types, how variable? | | Custom model vs prebuilt vs model-based |
| Does the target system have an API? | | Write vs file output |
| What error rate is acceptable? | | Confidence threshold and review load |

### Step 0-3. Baseline the manual process

| Measure | Today |
|---|---|
| Documents per month (and **pages** per month) | |
| Minutes per document | |
| People involved | |
| Known error rate | |
| Cost of an error | |
| Backlog | |

> ✅ **Exit criteria:** real documents in hand, four architecture questions answered, baseline
> captured, golden set agreed.

## Phase 1 — Prove Extraction (Week 2)

1. Run the worst 10 documents through Document Intelligence. Do this **before** any build.
2. Record what comes back, per document, per field.

| Doc | Type | Scanned? | Language | Fields expected | Fields extracted | Notes |
|---|---|---|---|---|---|---|

3. Test tables explicitly. Tables are where most pipelines quietly fail.
4. Test each language separately and report separately.

| Result | Action |
|---|---|
| Extraction works on the worst documents | Proceed |
| Fails on scans | Confirm the OCR path and model choice; do not fall back to text tooling |
| Tables garbled | Switch to layout-aware extraction |
| One language much weaker | Sequence rollout by language; say so now |
| Handwriting required | Reset the expectation immediately |

## Phase 2 — Classification and Extraction (Weeks 3–4)

### Step 2-1. Build classification

| Requirement | Verified |
|---|---|
| Closed class list agreed with the process owner | |
| `UNKNOWN` is a valid outcome routed to a human | |
| Multi-document files split before classification | |
| Classification confidence scored separately | |

### Step 2-2. Build extraction per class

Define the field schema explicitly. For each field:

| Field | Type | Required | Validation | Confidence threshold |
|---|---|---|---|---|

Rules that keep the pipeline honest:

- A field that cannot be found is **empty and flagged**, never inferred.
- Every extracted value carries its page and location.
- Never normalise silently — record the raw value alongside the normalised one.
- Never merge two candidate values into one.

### Step 2-3. Measure against the golden set

| Field | Documents | Correct | Empty when present | **Wrong value returned** |
|---|---|---|---|---|

The fourth column is the one that matters. An empty field creates a review task. A confidently wrong
value creates a business error.

## Phase 3 — Validation and Routing (Week 5)

### Step 3-1. Implement validation

| Layer | Implement |
|---|---|
| Format | Types, patterns, ranges |
| Master data | Supplier / part / customer lookups |
| Arithmetic | Totals, tax, line-item sums |
| Cross-field | Date ordering, currency consistency |
| Duplicate | Reference already processed |

A value that matches nothing in master data is low confidence, whatever the extractor says.

### Step 3-2. Set thresholds from measured data

1. Plot error rate against confidence, per field, using the golden set.
2. Choose the threshold that meets the agreed error rate.
3. Compute the resulting review volume.
4. Check it against actual reviewer capacity.

| Outcome | Action |
|---|---|
| Review volume is manageable | Set and monitor |
| Review volume exceeds capacity | Improve extraction, narrow scope, or renegotiate the error rate — explicitly |
| Review volume is near zero | Verify the threshold is not simply too permissive |

> 📌 A pipeline that routes 80% to review has not failed — if the manual process was 100%, that is
> still a 20% reduction. Say this out loud early so the number is not read as a failure later.

### Step 3-3. Build the review surface

| Requirement | Verified |
|---|---|
| Source document displayed beside the extracted fields | |
| Low-confidence fields highlighted | |
| Field click jumps to its location in the document | |
| Correcting a field is one action | |
| Reviewer can reject the whole document | |
| Corrections captured for accuracy tracking | |

See [Human-in-the-Loop Review & Approval](../../02-patterns/Human-in-the-Loop-Review-and-Approval/Human-in-the-Loop-Review-and-Approval.md).

## Phase 4 — Output (Week 6)

Build to whatever the downstream boundary actually permits.

| Boundary | Build |
|---|---|
| API available and writes approved | Write on human commit; record the transaction id |
| API available, writes not approved | Draft transaction for a person to commit |
| **No API** | File output in the exact import format the target expects |
| Manual entry only | Review-ready worksheet, ordered for fast keying |

For file output:

| Requirement | Verified |
|---|---|
| Format matches the target's import specification exactly | |
| Tested with a real import into a non-production target | |
| Failure of the import is visible, not silent | |
| Filename and location convention agreed | |
| Reprocessing does not create duplicates | |

## Phase 5 — Pilot (Weeks 7–8)

1. Run in **parallel** with the manual process for a full cycle. Both run; compare.
2. Measure per document: agent output vs human output.

| Metric | Target |
|---|---|
| Classification accuracy | ≥95% |
| Field extraction accuracy above threshold | ≥98% |
| **Wrong values passed above threshold** | **Near zero** |
| Documents routed to review | Within reviewer capacity |
| Handling time vs baseline | Measurably lower |
| Downstream import success | 100% |

3. Review every wrong value that passed the threshold. Each one is either a threshold problem or a
   validation gap.

| Signal | Action |
|---|---|
| Accuracy on target, review load manageable, time down | Go live on this type |
| Wrong values passing the threshold | Raise the threshold or add validation. Do not go live |
| Review load unmanageable | Narrow the scope to the highest-volume subtype |
| Downstream import failing | Fix before go-live; a broken import is worse than manual entry |

## Phase 6 — Operate and Extend

| Cadence | Activity | Owner |
|---|---|---|
| Daily (first 2 weeks) | Review corrections; look for systematic errors | Delivery engineer |
| Weekly | Accuracy per field and per language | Process owner |
| Weekly | Review queue volume and ageing | Operations lead |
| Monthly | Pages processed and cost vs forecast | Delivery engineer |
| Monthly | Poison-document queue triage | Delivery engineer |
| Quarterly | Re-run the golden set — catches supplier template drift | Delivery engineer |
| On new document type | Full Phase 1–5 cycle | Delivery engineer |

Template drift is the silent killer. Suppliers change their document layouts without telling anyone,
and accuracy decays gradually. The quarterly golden-set run is what catches it.
