# Sample Prompts & Test Cases — Document Processing & Extraction Agent

This scenario is mostly pipeline, not conversation. The test cases below matter far more than the
prompts.

---

## Extraction Instruction Block

```text
ROLE
You extract specified fields from <document type> for <Organisation>.

RULES
- Extract only the fields in the schema. Nothing else.
- Quote the value exactly as it appears. Record the raw value alongside any
  normalised value.
- Record the page and location of every extracted value.
- If a field is not present, return it EMPTY and flag it. Never infer,
  calculate, or assume a value that is not written in the document.
- If a field appears more than once with different values, return both and
  flag the conflict. Never choose.
- If part of the document is unreadable, name the affected pages. Never fill
  the gap.
- If the document is not a <document type>, say so and stop.
- Report a confidence score per field.

OUTPUT
Structured records only. No commentary, no summary, no interpretation.
```

The "never infer" rule is the whole thing. An empty field creates a review task; an invented one
creates a business error.

## Conversational Prompts (where a chat surface exists)

| Prompt | What good looks like |
|---|---|
| What did we extract from invoice 4471? | The fields with values, confidence, and source locations |
| Which documents are waiting for review? | Queue with reasons and ages |
| Why was this document flagged? | The specific field and the failed validation |
| Show me documents that failed processing this week | List with failure reasons |
| What's our extraction accuracy this month? | Per-field figures, per language |
| Which supplier's documents fail most often? | Ranked, with the failing field named — the template-drift signal |

## Document Test Cases

Every one of these should be in the test set before go-live.

| # | Document characteristic | Expected |
|---|---|---|
| 1 | Clean native PDF | All fields extracted, high confidence |
| 2 | Good-quality scan | All fields extracted |
| 3 | Poor scan / skewed / low contrast | Extracted with low confidence, or explicit failure. **Never a confident wrong value** |
| 4 | Photograph taken on a phone | Handled or explicitly rejected |
| 5 | Multi-page with a line-item table | Table extracted with row structure intact |
| 6 | Table spanning pages | Rows joined correctly, not duplicated |
| 7 | Multiple documents in one PDF | Split, each classified and extracted separately |
| 8 | Wrong document type submitted | Classified `UNKNOWN`, routed to human |
| 9 | Required field genuinely absent | `EMPTY` + flag |
| 10 | Field present twice with different values | Both returned, conflict flagged |
| 11 | Non-English document | Extracted, or explicitly declined |
| 12 | Mixed-language document | Handled or flagged. Never partially silent |
| 13 | Handwritten field | Flagged unreadable |
| 14 | Duplicate of a processed document | Detected, not reprocessed |
| 15 | Corrupt / password-protected file | Poison queue; pipeline keeps running |
| 16 | Very large file (100+ pages) | Processes or fails cleanly with a stated reason |
| 17 | Supplier changed their template | Accuracy drop detected by monitoring |
| 18 | Amounts using a different decimal separator | Normalised correctly, raw value retained |

## Validation Test Cases

| Case | Expected |
|---|---|
| Supplier not in master data | Low confidence, routed to review |
| Line items do not sum to the total | Flagged as an arithmetic failure |
| Tax does not compute | Flagged |
| Delivery date before order date | Flagged as a cross-field failure |
| Quantity far outside the normal range | Flagged for review |
| Currency inconsistent within the document | Flagged |
| Reference number in the wrong format | Flagged |
| Everything valid | High confidence, straight through |

## Confidence and Routing Tests

| Case | Expected |
|---|---|
| All fields above threshold | Straight through to output |
| One field below threshold | **Whole document** to review, that field highlighted |
| Classification uncertain | Review before extraction is attempted |
| Extraction succeeded, validation failed | Review, with the validation reason shown |
| Confidence high but the value is wrong | Investigate: threshold too low, or validation missing |

The last row is the one to hunt for in the pilot. Every instance is a defect in the threshold or
the validation layer, never an acceptable model error.

---

## Output Boundary Tests

| Case | Expected |
|---|---|
| API write approved | Written on commit; transaction id recorded |
| API write not approved | Draft created, never committed |
| **No API — file output** | File matches the target's import specification exactly |
| File imported into a non-production target | Import succeeds; verify before go-live |
| Import fails | Visible failure with the reason. **Never silent** |
| Document reprocessed | No duplicate downstream |
| Reviewer rejects a document | No output produced |

## Accuracy Reporting Format

Report like this, not as one blended number.

| Field | Language | Docs | Correct | Empty | **Wrong** | Confidence threshold |
|---|---|---|---|---|---|---|

A single "97% accurate" figure hides the fact that the amount field is 99% and the delivery date is
71%. Nobody can act on the blended number.

---

## What This Agent Should Never Do

| Behaviour | Why |
|---|---|
| Infer a value not written in the document | The core failure mode. Creates confident business errors |
| Calculate a missing field from other fields | Looks helpful, hides missing data |
| Choose between conflicting values | The document is ambiguous; a person decides |
| Silently normalise formats | The reviewer cannot see it happened |
| Pass an unreadable region as extracted | Fabrication |
| Write to a system of record without a human commit | Unless an approved measured error rate says otherwise |
| Blend accuracy across languages or document types | Hides the failures that matter |
| Reprocess a document into a duplicate downstream record | Reconciliation nightmare |
