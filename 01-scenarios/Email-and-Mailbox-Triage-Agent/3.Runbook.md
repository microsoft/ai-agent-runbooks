# Step-by-Step Guide — Email & Shared Mailbox Triage Agent

> **Platform**: Copilot Studio · Power Automate · Exchange Online
> **Target Readers**: Delivery engineer
> **Estimated effort**: 4–6 weeks, dominated by category discovery and downstream integration

---

| Requirement | Owner |
|---|---|
| Access to the shared mailbox, plus an export of 12 months of history | Customer |
| Downstream system write path confirmed | Platform team |

| Retention and records position on correspondence | Compliance |

## Phase 0 — Discover the Real Categories (Week 1)

The routing rules almost never exist in writing. Extracting them is the first work package.

### Step 0-1. Sample and label

1. Export 12 months of mailbox history.
2. Take a random sample of 300 messages — random, not curated.
3. Have the mailbox team label each with: what it was, where it went, what action was taken.

### Step 0-2. Build the category set

| Category | Definition (mutually exclusive) | Volume in sample | Routes to | Action |
|---|---|---|---|---|

Rules:
- Cap at ~10 categories. If the business wants more, design a two-level classification.
- Definitions must not overlap. Test by giving two people the same 20 messages to label — if they
  disagree, the definitions are not ready.
- Add an explicit `Unclear` category.

### Step 0-3. Baseline the manual process

| Measure | Today |
|---|---|
| Messages per year | |
| Minutes per message to triage | |
| Misroute rate (estimated by the team) | |
| Time to first response | |
| Backlog at peak | |

> ✅ **Exit criteria:** labelled 300-message sample, agreed category set with non-overlapping
> definitions, baseline captured, exception queue owner named.

## Phase 1 — Pre-processing (Week 2)

Build and test this before classification. It determines your ceiling.

| Step | Implementation | Tested |
|---|---|---|
| Trigger on mail arrival | Power Automate, scoped to the shared mailbox | |
| Filter noise | Auto-replies, bounces, newsletters, internal system mail | |
| Strip signatures and disclaimers | Pattern-based or model-based | |
| Isolate the newest message in a chain | Keep the thread as context, classify the newest | |
| Detect forwards and identify the true requester | | |
| Enumerate attachments, ignore inline images | | |
| Detect language | | |

Test on the raw 300-message sample. Measure how many survive pre-processing in a usable state.

> 📌 Filter noise **before** the agent runs. Every filtered message is consumption you do not pay for.

## Phase 3 — Build the Agent (Week 3)

1. Create the Copilot Studio agent in a solution, in a non-default environment.
2. Configure classification. Starting instruction block:

```text
ROLE
You classify incoming email for <Organisation>'s <mailbox name> shared mailbox.
You do not reply to anyone. You produce a classification and extract fields.

CATEGORIES
Classify each message into exactly one of:
- <Category A> — <definition>
- <Category B> — <definition>
...
- Unclear — the message does not clearly match any category above, or matches
  more than one.

RULES
- Classify the INTENT (what the sender wants), not the topic.
- Classify the newest message in the thread. Use earlier messages only as context.
- If the sender is forwarding on behalf of someone else, identify the original
  requester.
- If you cannot classify with confidence, return "Unclear". Never guess.
- Never invent a category that is not in the list above.

EXTRACT
For every message return:
- category
- confidence (high | medium | low)
- urgency (routine | priority | urgent) based only on stated deadlines or
  explicitly urgent language — never inferred from tone
- requester name and organisation
- <domain fields: reference number, account, order number, document requested>
For any field not present in the message, return "not stated". Never infer.

OUTPUT
Return structured data only. Do not write prose. Do not draft a reply.
```

3. Wire the confidence gate: `low` confidence or `Unclear` → human triage queue.
4. Wire the actions per category.

> 📌 Note the agent explicitly does **not** reply. Separating classification from response keeps the
> risky action behind its own gate.

## Phase 4 — Evaluate Against Real Mail (Week 4)

### Step 4-1. Hold-out test

Use 100 labelled messages the agent has never seen, from the Phase 0 sample.

| Metric | Result | Target |
|---|---|---|
| Overall classification accuracy | | ≥85% |
| Accuracy per category | | No category below 70% |
| False confident misroutes (high confidence, wrong) | | **≈0 — this is the critical one** |
| `Unclear` rate | | 5–15% is healthy |
| Field extraction accuracy | | ≥90% on required fields |

**A high-confidence misroute is worse than an `Unclear`.** A message in the exception queue gets
handled; a confidently misrouted one disappears into the wrong team. Tune for precision over
coverage.

### Step 4-2. Test the messy cases

| Case | Expected |
|---|---|
| Long reply chain | Classifies the newest message correctly |
| Forwarded on behalf of someone else | Identifies the true requester |
| Two requests in one message | `Unclear`, or the primary intent with a flag |
| Non-English message | Correct classification, or `Unclear` — not a wrong guess |
| Attachment carries the meaning | Correct, or `Unclear` if attachments are out of scope |
| Auto-reply | Filtered before the agent |
| Angry complaint | Routed, never auto-replied to |

### Step 4-3. Per-language accuracy

If the mailbox is multilingual, report accuracy **per language**. An 88% overall figure can hide
40% on a language that is 15% of volume.

---

## Phase 5 — Pilot in Shadow Mode (Week 5)

Run the agent **alongside** the human process without taking action.

1. Agent classifies and logs its decision.
2. Humans triage as normal.
3. Compare daily.

| Day | Messages | Agent agreed with human | Disagreements | Agent right in disagreement |
|---|---|---|---|---|

Shadow mode is the single most valuable phase in this scenario. It gives real accuracy on real mail
with zero risk, and it builds the mailbox team's trust — they see it working before it touches
anything.

Move to live only when agreement is stable and high-confidence misroutes are near zero.

---

## Phase 6 — Go Live and Operate

1. Enable actions for the **highest-confidence, lowest-consequence** category first. One category,
   not all of them.
2. Add categories weekly as each proves out.
3. Enable replies last, and only pre-approved templates.

| Cadence | Activity | Owner |
|---|---|---|
| Daily (first two weeks) | Review exception queue and every misroute | Delivery engineer |
| Weekly | Category accuracy trend | Team leader |
| Weekly | Exception queue depth and age | Queue owner |
| Monthly | Volume vs baseline; time-to-first-response | Business owner |
| On new category | Re-run the hold-out test | Delivery engineer |
| Continuous | Alert on zero throughput | Platform team |
