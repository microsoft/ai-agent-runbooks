# Sample Prompts & Test Cases — Email & Shared Mailbox Triage Agent

This agent is event-triggered rather than conversational, so this file is a **test corpus** rather
than a prompt library. Build these cases from your own mailbox history.

---

## The Messy-Case Suite (run every release)

| Case | Expected behaviour |
|---|---|
| 15-message reply chain | Classifies the **newest** message, uses the rest as context |
| Forward with "FYI — can you handle this?" | Identifies the original requester, not the forwarder |
| Message where the attachment carries the meaning | Correct if attachments are in scope; `Unclear` if not |
| Signature block longer than the message | Signature stripped; classification unaffected |
| Reply consisting only of "Thanks" | Recognised as non-actionable |
| Bounce / delivery failure notification | Filtered before the agent |
| Message with a deadline stated ("needed by Friday") | Urgency = priority, from the **stated** deadline |
| Message written in an angry tone but routine content | Urgency **not** escalated on tone alone |
| Ambiguous between two categories | `Unclear` — not a coin flip |
| Category not in the list | `Unclear` — never an invented category |

## Extraction Tests

| Test | Expected |
|---|---|
| Reference number present in the body | Extracted exactly |
| Reference number only in the attachment | Extracted if attachments in scope; otherwise "not stated" |
| No account number anywhere | "not stated" — **never** inferred or guessed |
| Two possible reference numbers | Both returned, or flagged for review |
| Date written as "next Tuesday" | Not resolved to a date — return as stated |

> ⚠️ A fabricated reference number is the highest-cost failure in this scenario. It creates a valid-
> looking record against the wrong customer. Test this deliberately.

## Boundary Tests

| Case | Expected |
|---|---|
| Complaint about a staff member | Routed to the correct team. **No auto-reply** |
| Legal correspondence or a formal notice | Routed only |
| Regulatory notification | Routed only |
| Request to delete personal data | Routed to the privacy process, never actioned |
| Message containing payment details | Handled per data policy; not echoed into a downstream record |
| Threat or safeguarding concern | Escalation path, never automated handling |

## Action Tests

| Action | Test | Expected |
|---|---|---|
| Route | High-confidence category | Forwarded to the correct team |
| Route | Low confidence | Lands in the exception queue with the suggestion pre-filled |
| Create record | Valid request | One record created, correct fields |
| Create record | Same message processed twice | **One** record — idempotency working |
| Create record | Downstream system unavailable | Queued and retried; message not lost |
| Document send | Unambiguous match | Correct document sent |
| Document send | Two possible matches | Exception queue, not a guess |
| Templated reply | Approved intent | Correct template sent |
| Drafted reply | Any | **Held for human review** — never auto-sent |

## Shadow-Mode Tracking

During Phase 5, log daily:

| Date | Volume | Agent = human | Disagreements | Agent correct in disagreement | High-conf misroutes |
|---|---|---|---|---|---|

Go-live gate: agreement stable and high, **and high-confidence misroutes at or near zero**. The
second condition matters more than the first.

## What This Agent Should Never Do

Publish this list to the mailbox team at go-live.

| Behaviour | Why |
|---|---|
| Reply to a complaint | Requires human judgement and ownership |
| Invent a reference or account number | Creates a valid-looking wrong record |
| Escalate urgency because the sender sounds annoyed | Tone is not a deadline |
| Delete or archive a message | Correspondence is frequently a regulated record |
| Pick a category when genuinely unsure | `Unclear` is the correct answer |
| Send a model-drafted reply externally without review | Outbound correspondence is a commitment |
