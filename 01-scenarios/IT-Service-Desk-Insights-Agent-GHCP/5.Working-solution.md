## Overview

This page describes how to package the agent built in [3.Runbook.md](3.Runbook.md) into an
importable, unmanaged Power Platform solution, and how to validate the import. Unlike a
scenario built around an inbound trigger, this one has no custom Dataverse table, no
environment variables, and no Power Automate workflows to export: the deliverable is a single
Copilot Studio agent, its attached skills, and the connection references its tools use.
The repository now includes a [ServiceNow-only local MVP](0.Resources/Working-solution/README.md).
It has not been bound, runtime-tested, exported, imported, or published. The remaining steps on
this page describe how to turn an approved local profile into a tenant-bound package.

### Current ServiceNow-only MVP

The local project enables `GetMyProfile`, ServiceNow knowledge reads, bounded incident reads,
and incident creation. Dynamics, updates, notes, attachments, closure, routing, and assignment
are absent. The MVP deliberately documents two reduced-scope choices: knowledge searches every
KB allowed by the signed-in connection because no fixed KB IDs were supplied, and incident
reads rely on ServiceNow impersonating the signed-in user and enforcing own-record ACLs.
Native `CreateRecord` ignores the full description, so the native tool contract sends only
`short_description`; the agent returns a manual handoff summary for the detailed evidence
afterward. See the
[working-solution README](0.Resources/Working-solution/README.md) for the exact status.
PAC 2.12.2 serializes all ten agent components but omits the tool-to-connection association
asset and verified connector icon metadata, so the validation ZIP is not an importable release.

### What the exported solution would contain

| Component | Expected content |
|---|---|
| Agent | The GHCP agent from [Step 1](3.Runbook.md#step-1-create-one-agent-on-the-github-copilot-harness), with the instructions from [Step 5](3.Runbook.md#step-5-package-agent-instructions-and-skills) and the model approved for your tenant |
| Skills | Only the skills in the approved profile, uploaded from [0.Resources/Skills](0.Resources/Skills/README.md); each skill's YAML `name` matches the [Capability matrix](0.Resources/Capability-matrix.md) |
| Tools | The native ServiceNow connector actions selected in [Step 6](3.Runbook.md#step-6-apply-onoff-controls); optional Dynamics actions appear only in an extension profile |
| Connection references | Office 365 Users (`GetMyProfile`) and ServiceNow for the baseline; add Dynamics Customer Service only when the optional extension is enabled |
| Environment variables | None. Routing, assignment, and closure eligibility are backend policy, not agent-configured values |
| Dataverse table | None. The baseline reads and writes ServiceNow directly; the optional Dynamics extension uses the existing Case table rather than a custom staging table |

The absence of a table and workflows is a direct result of the architecture decision in
[2.Architecture.md](2.Architecture.md): one agent calling narrow, backend-governed tools,
not an event-triggered automation with its own data store.

## Prerequisites

| Requirement | Details |
|---|---|
| Environment | A development or test Copilot Studio environment with the GitHub Copilot harness enabled and Copilot Credits allocated, separate from any production profile |
| Import/export rights | A security role that can create and export solutions, such as System Administrator |
| ServiceNow | A non-production instance with the knowledge base, catalog, and incident table reachable by the connector, per [Step 2](3.Runbook.md#step-2-configure-servicenow-capabilities) |
| Dynamics 365 Customer Service (optional) | Required only for the cross-system handoff extension; provide a non-production environment with the Case table reachable by the connector |
| One account | The account that exports and later imports the solution should own every connection used by the agent's tools, so published Preview sessions resolve consistently |
| Test records | Sanitized knowledge articles and incidents, plus cases only when testing the optional Dynamics extension, per [0.Resources/README.md](0.Resources/README.md) — never production personal data |

## Step 1. Package and Export the Agent as a Solution

1. In the source environment, complete [Steps 0–7 of the Runbook](3.Runbook.md) so the agent,
   its skills, and its tools are in the approved ON/OFF state.
2. In Copilot Studio, select the environment, open **Solutions**, and create a new unmanaged
   solution (for example, publisher prefix `contoso`, matching your tenant's convention).
3. Add the agent to the solution. Copilot Studio includes its attached skills and the
   connection references its tools use automatically; it does not re-export backend
   authorization, field configuration for each included backend, or the capability matrix itself.
4. Export the solution as a zip. Store it in an access-controlled location, not this public
   repository — the zip can embed tenant-specific connection metadata.

Not every agent component is guaranteed to round-trip through export and import; Microsoft
documents this in [Export and import agents using solutions](https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-solutions-import-export).
Step 2 below exists because of that gap, not as an optional formality.

---

## Step 2. Import and Check the Imported Components

1. In the target environment, import the zip from **Solutions > Import solution**. On the
   **Connections** page, map Office 365 Users and ServiceNow. Map a Dynamics connection only
   when the optional extension is included.
2. After import, open the solution and select **Publish all customizations**.
3. Open the agent and check it against the source configuration:

   | # | Check | Expected |
   |---|---|---|
   | 1 | Instructions | Match the prompt from [Runbook Step 5](3.Runbook.md#step-5-package-agent-instructions-and-skills) |
   | 2 | Model | The model approved for your tenant |
   | 3 | Skills | **Build > Skills** lists exactly the skills in the approved profile; no extra or missing capability |
   | 4 | Tools | **Build > Tools** lists only the connector actions in the approved profile; none asks for a connection. If one does, select or create a connection with the account from the prerequisites |
   | 5 | `GetMyProfile` | Bound to the importing user's own Office 365 Users connection, not a shared or maker-owned one |

4. Publish the agent once the checks pass.

---

## Step 3. Test the Imported Agent

Reuse [4.Sample-prompts.md](4.Sample-prompts.md) directly — there is no separate test set for
the imported copy. Run, at minimum, one Preview test per enabled capability:

| Test | Prompt source | Expected result |
|---|---|---|
| Grounded knowledge answer | [Starter Prompts](4.Sample-prompts.md#starter-prompts-configure-these-in-the-agent) | Answer cites its ServiceNow KB/catalog source; no record is created |
| Existing-record read | [Starter Prompts](4.Sample-prompts.md#starter-prompts-configure-these-in-the-agent) | Only bounded incidents owned by the impersonated ServiceNow user are returned; another user's record remains inaccessible by search and direct `sys_id` |
| Incident creation | [Combined Scenario 1](4.Sample-prompts.md#combined-scenario-1---knowledge-guided-investigation-and-creation) | Native MVP creates a ServiceNow incident with confirmed `short_description`, returns the detailed manual handoff, and sets no queue or owner |
| Optional Dynamics handoff | [Combined Scenario 2](4.Sample-prompts.md#combined-scenario-2---optional-dynamics-case-handoff) | Run only for the extension; case creation preserves the ServiceNow context without agent routing |
| Requester-only closure | [Combined Scenario 3](4.Sample-prompts.md#combined-scenario-3---requester-closes-their-own-servicenow-incident) | The record's own requester succeeds; a different requester or a privileged technician is denied |
| Capability OFF | Any disabled capability's prompt | Agent explains the limitation; no alternate tool or workflow completes the action |

Check the actual tool calls in Preview's run detail, not just the reply text, exactly as
[How to Use These Prompts](4.Sample-prompts.md#how-to-use-these-prompts) describes for the
source agent.

---

## Step 4. Clean Up

1. Delete the test incidents created in ServiceNow. If the optional Dynamics extension was
   tested, also delete its test cases.
2. Confirm no capability was left ON beyond the approved profile before handing the environment
   back or promoting toward [Step 8](3.Runbook.md#step-8-publish-and-hand-over).

There are no table rows, environment variable values, or workflow runs to reset, because this
scenario has none of those components.

## Troubleshooting

| Symptom | Likely cause and action |
|---|---|
| The import fails | Check the error on the **Solutions** page for the missing component or privilege; import with an account that can create solution components |
| A tool asks for a connection | In **Build > Tools**, select or create a connection with the account from the prerequisites |
| `GetMyProfile` returns nothing for the importing user | Guest/external accounts can fail this lookup; test with a licensed, directory-known account |
| The agent answers but cites no source | The knowledge/catalog permission for the connected account was not carried over; reconfirm it in the target environment |
| A disabled capability still appears to work | The skill was removed but its underlying connector action is still exposed in **Build > Tools**; disable the action, not just the skill |
| Closure succeeds for the wrong user | Backend requester verification was not reconfigured in the target system; this is a backend policy gap, not an agent setting |
