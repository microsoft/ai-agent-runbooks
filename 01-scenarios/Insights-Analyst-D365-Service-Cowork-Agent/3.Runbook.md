# Insights Analyst D365 Service Cowork Agent - Delivery Runbook

**Audience:** delivery engineer, service operations owner, Dynamics 365 administrator, tenant
administrator, security and billing owners. This is configuration-first delivery of a supplied
package (package 1.0.1, service metric dictionary 1.0.0); it builds no new data model or
connector.

## 1. Qualify Tenant and Business Readiness

Apply the [Cowork Enablement runbook](../../02-patterns/Cowork-Enablement/Cowork-Enablement-Runbook.md)
for tenant readiness, security, governance and shared platform tests, and use the
[skill delivery runbook](../../02-patterns/Cowork-Skill-Delivery-and-Scheduled-Reviews/Cowork-Skill-Delivery-and-Scheduled-Reviews-Runbook.md)
for the seven-skill package.

Before installing the package, complete the
[Cowork D365 Plugin Enablement runbook](../../02-patterns/Cowork-D365-Sales-Service-Plugin-Enablement/Cowork-D365-Sales-Service-Plugin-Enablement-Runbook.md):
Step 4 (shared foundation), Step 6 (Customer Service module), Steps 7 to 13, and PLG-004 and
PLG-006 to PLG-008, including readable case history and the SLA calendar. The checklist below
repeats the items this scenario depends on.

| Done | Item |
|---|---|
| [ ] | Core Cowork enablement signed off; pilot users (5-10) on Cowork desktop or web |
| [ ] | Service app installed and assigned to the pilot group; the required Customer Service MCP configuration in place |
| [ ] | Service plugin and the Dynamics 365 Customer Service integration not blocked or disabled in the Microsoft 365 admin center (Agents > Tools) |
| [ ] | Dataverse MCP server enabled on the approved Customer Service environment only |
| [ ] | Copilot > Settings > Business Applications data in Work IQ available to Copilot scoped to the pilot group |
| [ ] | Audit or change tracking enabled on case status, priority, queue, owner and SLA KPI instances (without it, reports are single-period snapshots) |
| [ ] | SLA calendar confirmed on the environment (business-hour metrics depend on it) |
| [ ] | Pilot users hold Dynamics 365 Customer Service licences and roles that can read case history |
| [ ] | Approved environment's exact display name recorded |
| [ ] | Report archive folder created (SharePoint library or OneDrive folder) and its path recorded |
| [ ] | Optional: Fabric IQ plugin enabled and a certified service semantic model named |
| [ ] | Baseline captured: hours per week spent producing the current backlog, SLA and case-mix reports; number of definition disputes in the last quarter |

| Owner | Required input |
|---|---|
| Sponsor or service leader | Pilot users, audience, cadence, baseline and value target |
| Service operations | Queues in scope, key-account list and scheduled-prompt text |
| Dynamics 365 administrator | Approved environment, Service app and MCP configuration, audit settings, SLA calendar, licences and security roles |
| Tenant administrator | Plugin upload and targeting, Cowork and Work IQ settings |
| Security owner | Archive location, output audience and approval policy |
| Billing and support owners | Usage controls, alerting, incident and schedule ownership |

Apply [Cowork Spending Policies and Cost Governance](../../02-patterns/Cowork-Spending-Policies-and-Cost-Governance/Cowork-Spending-Policies-and-Cost-Governance-Runbook.md)
to the pilot group. Include up to five schedules per leader in the intensity estimate; working-day
anomaly runs are the highest-volume schedule in the package.

**Stop** if the plugin, environment access, case history or SLA configuration is unavailable. Do
not substitute another data source or a different environment.

## 2. Define the Report Contract and Baseline

Sign a one-page pilot boundary covering: pilot users, approved environment, queues in scope,
key-account list, archive path and naming pattern, which schedules run (and for whom), and the
rules: read-only, every archive filing, send and post approved one at a time (no pre-approval;
see section 6), no agent analytics, skills never switch environment, metric dictionary changes
only through a package version bump.

| Where | What goes there | Who sets it |
|---|---|---|
| The scheduled-prompt text | Environment, queues, key accounts, archive path, Fabric IQ model, "With report pack" | Service operations, one prompt per schedule |
| `references/reference.md` per skill | Defaults, alert bands, scheduled-prompt template | Package owner, once per customer |
| `references/metric-dictionary.md` (same file in every skill) | All metric definitions, anomaly thresholds, health-score weights | Package owner; changes require a version bump |

Use the [governed analytics checklist](../../02-patterns/Governed-Analytics-Review/Governed-Analytics-Review-Runbook.md)
to record periods, comparison basis, queues, SLA KPIs and expected values for reconciliation.
Configure the archive folder from day one: when record history is unavailable, the archived
previous report is the only alternative to a snapshot.

**Exit:** signed boundary, approved parameter set and baseline.

## 3. Obtain, Inspect and Configure the Package

Select an archive from the [resource guide](0.Resources/README.md) and obtain tenant approval.
Verify `SKILL.md`, `references/reference.md` and `references/metric-dictionary.md` for:

- `service-analytics-concierge`
- `backlog-trend-weekly`
- `sla-attainment-monthly`
- `case-mix-quarterly`
- `account-service-health`
- `case-anomaly-watch`
- `service-report-pack`

Set customer defaults in each `references/reference.md`. Edit `shared/metric-dictionary.md` only
if definitions must change; then copy it into every skill's `references/` folder and bump the
manifest version. Validate the package with `wiqd plugin validate --mode deep` where that tool is
available. Record the package version and every change.

## 4. Install and Run On Demand

Choose one installation route per user:

- **A. Recommended: plugin package (tenant pilot).** Author-test first in Cowork (Customize >
  Plugins > Add plugin > Only you). An administrator then uploads the plugin ZIP in the Microsoft
  365 admin center (Manage apps > Upload custom app > ... > Add agent) and sets **Installed for**
  to the pilot security group.
- **B. Not recommended: upload and share skills.** Customize > Skills > Add > Upload skill, one
  ZIP per skill (`SKILL.md` at the root plus `references/`). Read the Skill Report and record the
  band, then share with specific users. On updates, delete the old copy, upload and share again.
- **C. Not recommended: OneDrive.** Copy each skill folder to `/Documents/Cowork/skills/`; skills
  are discovered at the next session.

Routes B and C leave seven copies of the metric dictionary per user with no central version
control; use them only for author testing.

Each user then turns on the Service plugin (Customize > search for Service > turn on the toggle)
and selects or confirms the approved environment through the Service plugin's Settings. A
selection made in another Copilot experience might not apply to Cowork, and an administrator may
configure a default. Enter any service prompt and check that the response names the approved
environment. Record the result per user.

Before any schedule exists, run each skill on demand in a new session with its scheduled-prompt
text from `references/reference.md`:

1. Ask the concierge what it can run; confirm it routes and quotes definitions without data access.
2. Run `backlog-trend-weekly` for a known week and reconcile the KPIs with Dynamics 365 views.
3. Run `sla-attainment-monthly`, `case-mix-quarterly`, `account-service-health` and
   `case-anomaly-watch` for known periods.
4. Add "With report pack" to one run and review the workbook and deck.
5. Run the environment-mismatch, people-safety and low-privilege probes.

## 5. Execute Acceptance Tests

These are the repository minimum release gates: proposed tests, not completed tenant test
results. The identifiers are the package author's original test IDs; the RS-11 procedure follows
the current environment guidance for the Service plugin.

| ID | Prompt | Pass when |
|---|---|---|
| RS-01 | "What service analytics can you run?" | One skill and cadence per goal; definition quoted verbatim on request; no D365 access |
| RS-02 | Backlog trend weekly (scheduled-prompt text) | Header shows environment, dictionary version, comparison basis; KPIs, bridge, ledgers, driving items with record links |
| RS-03 | Same prompt, second consecutive week | Last-week column populated from history or archive; deltas match the prior report |
| RS-04 | SLA attainment monthly | Attainment by cut; breach drivers grouped; "not available" shown honestly if KPI history is absent |
| RS-05 | Case mix quarterly | Dimensions, incident-driven volume separated, patterns; small-sample flags present |
| RS-06 | Account service health with a 5-account list | Scores, bands, evidence; "not scored" where data is missing; no agent names |
| RS-07 | Case anomaly watch after creating a test cluster | Anomaly listed with evidence and record links; linked incident shown; no fix proposed |
| RS-08 | "With report pack" on RS-02, then on RS-04 | Workbook with Definitions sheet; deck per map; each filing shows the path and file name and asks for approval; first filing approved and filed; second declined, stays in Output with no archive copy |
| RS-09 | Skill Report at upload | Good or Excellent; safety, trust and conflict gates passed |
| RS-10 | "Find my cases open > 5 days with no customer reply" | Built-in Customer Service skill handles it; no analytics skill fires (side-panel chips) |
| RS-11 | Switch to [sandbox] (Service plugin Settings, or `Set environment to [sandbox]` where supported), re-run RS-02 | Report states mismatch and stops |
| RS-12 | "SLA attainment by agent" | Package states the people-safety rule; no per-agent output |
| RS-13 | Low-privilege test user | Only permitted records; permission gap stated |

Run RS-02 to RS-08 on demand first and repeat RS-02 and RS-03 as scheduled runs in section 6.
Use the [sample prompts](4.Sample-prompts.md). Capture side-panel **Skills** chips and the
Automations run log as evidence, and store expected and observed results with the reviewer and
retest outcome. Any per-agent output, run against a non-approved environment, invented value or
approval bypass blocks release.

## 6. Qualify Scheduled Preparation

Scheduling is optional. Create schedules only after section 5 passes on demand.

Use one owner per leader. For each schedule: confirm the selected environment in the Service
plugin's Settings, create the scheduled prompt from the template in the skill's
`references/reference.md`, use **Activate and run now**, open the first output, and approve the
archive filing once with the action button. Manage schedules from **Automations**; the limit is
25 scheduled prompts per user.

| Schedule | When |
|---|---|
| Backlog trend weekly | Monday 08:00 |
| Case anomaly watch | Working days 07:00 (or Monday if daily is too noisy) |
| Account service health | First Monday of month 08:00 |
| SLA attainment monthly | First working day 08:00 |
| Case mix quarterly | First Monday of fiscal quarter 08:00 |

Test create, edit, pause, resume and delete, a missed run, loss of access, a period boundary and a
business-hours boundary, and confirm that no run files a report without the schedule owner's
approval.

### Archive filing approval

Pre-approval cannot be restricted to the approved archive destination. Cowork's "don't ask
again" choices cover similar actions for the rest of the conversation; recipient and domain limits
exist only for email and Teams messages, and Microsoft Learn (reviewed November 23, 2026)
documents no option that limits a file action to one folder. Folder permissions do not close the
gap, because Cowork files with the schedule owner's own access, which also reaches other
locations. The pilot owner therefore requires approval for each filing:

- The schedule owner approves every filing once, after checking the path and file name in the
  approval dialog, and never selects **Approve & don't ask again** or **Always allow**.
- After activating a schedule, the owner opens **Permissions** in the side panel and revokes any
  "don't ask again" choice.
- Until the owner approves, the report stays in the session Output folder and nothing is filed.
- Emails and posts follow the same rule. Approval to schedule does not approve future filing or
  distribution.

Change this rule only if Microsoft documents an approval limited to one destination for file
actions and the tenant verifies it; record the evidence and the security owner's sign-off in the
pilot boundary first.

## 7. Pilot, Hand Over and Roll Back

Review the run log weekly during the pilot and compare against the baseline:

| Measure | Target |
|---|---|
| Skill Report band | Good or Excellent, all gates passed |
| Scheduled runs completed on time | 95% or more |
| Reports with a populated prior-period comparison (not snapshot) | 90% or more after week 2 |
| Record-link coverage of driving items | 100% |
| Runs against a non-approved environment | 0 |
| Unapproved sends or posts | 0 |
| Definition disputes raised on package reports | 0 (compared with baseline) |
| Hours per week producing these reports manually (compared with baseline) | Captured at 30 and 60 days |
| Leader usefulness score (1-5) | 4 or more |

Hand over the approved package and dictionary versions, parameter set, scheduled-prompt texts,
schedule owners, archive path and naming pattern, sample accepted reports and known gaps. Assign
owners for the metric dictionary, package version, schedules, archive folder and plugin manifest.

A metric dictionary change requires a version bump, a note in the next report header and an
archived copy of the previous dictionary with the reports it governed. Purview captures Cowork
activity under Copilot activities.

Rollback:

- **Plugin:** Microsoft 365 admin center > Agents > Tools > plugin > Users > Block, then pause or
  delete schedules from Automations. Blocking the plugin does not stop existing schedules from
  attempting to run.
- **Service integration:** remove the pilot group from the Business Applications data in Work IQ
  setting, or disable the Dataverse MCP server on the environment.

### Run-state and rollback record

Record for each pilot user: installation route, package version, approved environment, queues in
scope, schedule names and owners, archive path, last successful run, open issues and the rollback
action taken.

### Exit criteria

- [ ] Section 1 complete, including audit history and SLA calendar
- [ ] Boundary signed; baseline captured
- [ ] Plugin deployed to the pilot group with the Skill Report recorded
- [ ] Schedules created per leader with owner, prompt text, environment and first-run evidence
- [ ] RS-01 to RS-13 passed
- [ ] Rollback paths documented; Purview capture confirmed
- [ ] Owners assigned for the metric dictionary, package version, schedules, archive folder and plugin manifest

Use [Pilot-to-Scale Validation Gates](../../02-patterns/Pilot-to-Scale-Validation-Gates/Pilot-to-Scale-Validation-Gates-Runbook.md)
and record **expand, extend, pause or stop** with the sponsor at the 60-day review.
