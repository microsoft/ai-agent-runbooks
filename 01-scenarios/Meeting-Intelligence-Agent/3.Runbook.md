# Step-by-Step Guide — Meeting Intelligence & Action Tracking Agent

> **Platform**: Copilot Studio · Teams · Work IQ / Teams MCP · CRM or work tracker
> **Target Readers**: Delivery engineer
> **Estimated effort**: 4–6 weeks; consent and scoping dominate the front end

---

## Prerequisites

| Requirement | Owner |
|---|---|
| Transcription enabled and lawfully consented for the meetings in scope | Customer legal / HR |
| Works council or employee representative agreement, where applicable | Customer |
| A specific meeting series to pilot on — not "all meetings" | Business owner |
| Target system for actions, with a write path | Platform team |
| Named chair or owner who will review the capture | Business owner |

---

## Phase 0 — Consent and Scope (Week 1, do not skip)

### Step 0-1. Clear the legal position

| Question | Answer | Signed by |
|---|---|---|
| Is transcription lawful and consented in every jurisdiction in scope? | | |
| Do works councils need to agree? Have they? | | |
| Are external participants informed? | | |
| Can output ever be used to assess an individual? | | |
| Retention period for transcripts and derived records? | | |

**If "can this assess individuals" is not a firm no, stop here** and involve HR and employee
representatives.

### Step 0-2. Scope the meeting categories

| Category | In scope? | Rationale |
|---|---|---|
| Team / project cadence | | |
| Account or client meetings | | |
| Leadership / strategy | | |
| HR, disciplinary, performance | **No** | |
| Legal, M&A, confidential | **No** | |

Explicitly excluded categories must be enforceable — by meeting series, by organiser, or by an
opt-in model. "We'll be careful" is not a control.

### Step 0-3. Pick one series to pilot

One recurring meeting, one owner, one target system. Resist enterprise scope.

> ✅ **Exit criteria:** legal position signed, excluded categories enforceable, single pilot series
> chosen with a named reviewer.

| Question | Answer |
|---|---|

| Will the team actually open that system? | |
| Write API available? | |
| How is draft status represented **in that system**? | |
| Stable identity for deduplication across recurrences? | |

Build and test the write standalone before wiring the agent to it.

> 📌 If the honest answer to "will the team open that system?" is no, change the target. Capture
> written somewhere nobody reads is the most common silent failure in this scenario.

## Phase 2 — Build the Extraction Agent (Week 3)

Create the agent in a solution, in a non-default environment. Starting instruction block:

```text
ROLE
You extract structured outcomes from meeting transcripts for <Organisation>.
You record what was said. You do not interpret, advise, or evaluate people.

EVIDENCE RULE — this overrides everything else
Every decision, action, and risk you output MUST include a verbatim quote from
the transcript showing where it was agreed. If you cannot quote it, do not
output it. Never infer a commitment that was not spoken.

OUTPUT
1. Summary — maximum 5 bullets, factual, no interpretation.
2. Decisions — each with the verbatim quote.
3. Actions — each with:
   - the action, as agreed
   - owner: ONLY if a person was named or clearly self-assigned.
     Otherwise "Owner not assigned".
   - due date: ONLY if a date or timeframe was stated.
     Otherwise "No date agreed".
   - the verbatim quote
   - confidence: high if named and dated, otherwise low
4. Risks and blockers — each with the verbatim quote.
5. Open questions — items raised but not resolved.

OWNERSHIP RULES
- "Sarah will do X" -> owner Sarah.
- "I'll pick that up" -> owner is the labelled speaker, flag
  "confirm owner" because speaker labels are unreliable.
- Implied or assumed ownership -> "Owner not assigned".
- Never assign an owner based on who talked most about a topic.

BOUNDARIES
- Do not characterise any participant's tone, attitude, engagement or
  performance.
- Do not summarise what someone "seemed to think".
- Do not assess whether the meeting was effective.
- If the transcript is too poor to extract reliably, say so and stop.

STATUS
Everything you produce is a DRAFT for human review. Label it as such.
```

The evidence rule and the ownership rules are the two blocks that make this deployable. Do not
soften them to improve coverage.

## Phase 3 — Test on Real Transcripts (Week 4)

### Step 3-1. Build the test set

At least 15 real transcripts spanning:
- 3 clean, well-run meetings
- 3 with heavy cross-talk
- 3 with non-native speakers or a second language
- 2 with poor audio
- 2 where no actions were agreed at all
- 2 recurring instances of the same series

### Step 3-2. Score against a human baseline

Have the chair independently list the actions and decisions. Compare.

| Metric | Target |
|---|---|
| Actions correctly captured (recall) | ≥85% |
| **Actions invented (not in transcript)** | **0 — hard fail** |
| Owners correctly assigned | ≥90% of those the agent assigned |
| Owners incorrectly assigned | ≈0 |
| Decisions correctly captured | ≥85% |
| Meetings with no actions → empty output | 100% |

**A single invented action fails the release.** Missing an action is recoverable — the chair adds
it. An invented one with a named owner and a date gets acted upon.

### Step 3-3. Deduplication test

Run two consecutive instances of the same recurring series. Expect: one action, updated — not two.

---

## Phase 4 — Pilot (Week 5)

1. Run on the single chosen series.
2. Chair reviews every capture before it commits.
3. Track review effort and corrections.

| Week | Meetings | Actions captured | Corrections | Invented actions | Chair review minutes |
|---|---|---|---|---|---|

Go-live gate: zero invented actions across the pilot, and chair review under five minutes per
meeting. If review takes longer than writing notes by hand, the design is wrong.

---

## Phase 5 — Add the Tracking Loop

Only after capture is trusted. This is what makes the scenario stick.

1. **Outstanding action report** — open items by owner and age.
2. **Reminders** — before the next occurrence of the series.
3. **Pre-meeting context pack** — outstanding actions surfaced to the chair beforehand.
4. **Escalation** — overdue items flagged, per an agreed policy.
5. **Closure** — only on explicit confirmation, never inferred.

The loop is the value. Capture alone produces tidy notes; the loop produces kept commitments.

---

## Phase 6 — Expand and Operate

Add one meeting series at a time. Re-run the extraction test for each new series — meeting culture
varies more than you expect between teams.

| Cadence | Activity | Owner |
|---|---|---|
| Per meeting (pilot) | Chair reviews capture | Chair |
| Weekly | Corrections analysis; any invented actions | Delivery engineer |
| Monthly | Action closure rate and ageing | PMO / business owner |
| Monthly | Review effort per meeting | Business owner |
| On new series | Re-run extraction tests | Delivery engineer |
| Quarterly | Re-confirm consent position | Compliance |

- [ ] Zero invented actions across the test set
